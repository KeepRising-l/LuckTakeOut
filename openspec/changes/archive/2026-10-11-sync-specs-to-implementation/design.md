# Design

## Context

与本 change 做法直接相关的现状：

- 代码已完成一轮推进并验证通过（29 项测试、`manage.py check`、`makemigrations --check` 无待生成迁移、三端构建通过）。
- `openspec/specs/` 下 5 个 capability 的描述停留在推进之前：`order-lifecycle` 仍在写"接单后状态仍为待接单"，`customer-ordering` 仍在写"配送费由请求携带"，`platform-ops` 仍在写"只有 AI 工具调用写日志"。
- 状态取值统一为后端整数枚举（10–60）已在 `thesis-docs/03-系统设计.md` 的 2.3 定稿，三端文案映射集中在 `web/packages/shared/src/orderStatus.ts`。
- 已归档基线 change 的落差表原有 11 条，前 3 条已由 `enforce-server-side-scope` 消化，本 change 覆盖其后的 7 条，仅剩「商户入驻链路」1 条。

## Goals / Non-Goals

**Goals:**

- 让 5 个 capability 的规格与实现一致，`openspec validate --specs` 继续通过。
- 把"接单即进入配送中""配送费为平台固定值""非法迁移被拒绝"这三条容易反复的口径，写成明确的 WHEN/THEN 断言，使它们在回归时可被直接验证。
- 显式记录"实现先行、规格后补"这一次倒序，避免它被无声地正常化。

**Non-Goals:**

- 不改动任何代码。本 change 的范围就是规格文本。
- 不实现「商户入驻链路」，它另开 change。
- 不把实现细节（函数名、装饰器、表名）写进规格：本次新增的断言只描述可观察行为。

## Decisions

### 决策一：只补规格，不返回去改代码

规格的描述向实现对齐，而不是把实现改回规格描述的样子。

- 理由：实现是按 `02-需求分析.md` 第 3 稿做的，规格只是没有跟上；待对齐的一方是规格。若反过来让实现迁就规格，等于让文档否掉需求。
- 被否决的替代方案：把这一轮代码回滚，重新走 propose → apply → archive。否决理由是代码已验证通过、且正确反映了需求，回滚只为了形式上的顺序一致，代价与收益不成立。

### 决策二：新增「状态迁移合法性」为 order-lifecycle 的一条独立需求

状态机的合法迁移表与终态约束，从原先散落在各端需求里的隐含约定，提升为 `order-lifecycle` 下一条独立需求。

- 理由：它是订单生命周期的固有约束，被顾客支付、顾客取消、商户接单与取消、骑手接单与送达共同依赖；放在任一端的需求里，其余端就只能靠推理得知约束存在。
- 被否决的替代方案：把"非法迁移被拒绝"分别写进各端的操作需求。否决理由是同一张迁移表会被声明五次，任一处改动都会留下不一致。

### 决策三：状态取值口径不进规格，只在规格中断言"以统一整数返回"

三端文案映射、各端视角措辞（商户端把 30 呈现为"已接单，待骑手取餐"）属于设计层，保留在 `03-系统设计.md` 的 2.3，规格只断言"订单状态以系统统一的整数取值返回"。

- 理由：规格描述外部可验证的行为，文案属于呈现层选择，写进规格会在每次文案调整时触发规格变更。
- 被否决的替代方案：把取值与文案对照表抄进规格。否决理由同上，且会与设计文档形成两处维护。

### 决策四：展示口径的断言写成"不包含什么"

涉及展示的需求，除正面断言（评分是评价均值）外，补上"不包含销量、距离、评分、收入、预计时长"这类否定断言。

- 理由：这一轮清理的正是硬编码的假值。假值往往以"多返回字段"的形式复发，只断言正面行为无法发现它再次出现；否定断言可以直接挡住。
- 权衡：否定断言会随功能扩展而过时（例如今后真的上线了距离计算，需要主动删除该断言）。这是可接受的，因为删除一条明确写下的断言，远比发现一个悄悄爬回来的假值容易。

## Risks / Trade-offs

- [本 change 记录的是已完成的实现，任务清单没有"未完成"的推进过程] → 在 proposal 与 tasks 中显式写明"实现先行"，并把这一点作为流程教训记下，避免它被视为正常做法。
- [规格向实现对齐，可能出现"实现怎么做就怎么写"的自我循环] → 本次对齐的每一条都能在 `02-需求分析.md` 第 3 稿里找到对应要求（配送费为平台固定值、骑手接单即进入配送中、商户列表不展示销量与距离），不是凭实现反推需求。
- [否定断言（不包含距离、收入等）今后可能过时] → 已在上文记录取舍；如未来上线相关能力，需主动修订对应需求。
- [规格数量增加带来维护成本] → 本次仅新增 1 条需求、修订 7 条，且新增的那条被多端共同依赖，摊薄后成本为正收益。
