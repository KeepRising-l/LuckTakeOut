# Design

## Context

参见 `proposal.md` 的 Why。这里只记与本 change 做法直接相关的现状与约束：

- `thesis-docs/02-需求分析.md` 为第 3 稿（按最小可行范围收敛：两档优先级、商户注册与入驻合并为一步、骑手接单即进入配送中、配送费为平台固定值），是需求的唯一权威。
- 系统实现已在 `takeout/`（Django 后端）与 `web/`（Vue 3 三端 SPA）中存在并可用。
- OpenSpec 侧此前为空：`openspec/specs/` 与 `openspec/changes/` 均只有占位文件，`openspec view` 显示 0 specs / 0 changes。
- 已核对出 **11 条落差**（见 `proposal.md` 落差表），全部是"第 3 稿要求、代码未达标"；另有若干能力被第 3 稿移入"本期不包含"，它们既不属于落差、也不进入基线。
- `openspec/config.yaml` 已写入项目 context 与按产物的 rules。

## Goals / Non-Goals

**Goals:**

- 建立 6 个 capability 的基线规格，使后续每条落差都有一个可比较的基准，`openspec validate` 可通过。
- 把"02 的编号"与"specs 的需求"建立可双向对照的引用关系，让需求在文档与规格之间不靠记忆维系。
- 让 `openspec/archive` 之后的 main specs 成为"系统当前确实做到的事"的可信描述。

**Non-Goals:**

- 不改动 `takeout/` 与 `web/` 的任何代码。
- 不改动 `thesis-docs/`（02 保持权威，specs 不进入论文交付物）。
- 不在本 change 内修正 11 条落差；每条落差按主题另开 change。
- 不覆盖第 3 稿的"本期不包含"项：这些能力本期不做，规格中不出现，落差表中也不登记。

## Decisions

### 决策一：派生方向定为 02 → specs

`thesis-docs/02-需求分析.md` 是权威源，`openspec/specs` 是从它派生的可验证投影。需求变更时先改 02，再同步 specs。

- 理由：02 的章节与编号受学校模板与答辩场景约束，改动成本最高；specs 是工程侧的验收依据，可以随时从 02 重建。把成本高的一方定为权威，可以避免"两份都要改"的拉锯。
- 被否决的替代方案：以 specs 为权威、由它反推 02。否决理由是规格使用 WHEN/THEN 场景句式，写成论文的"需求分析"章节不符合学校模板，反推会额外产生一次翻译工作，且翻译损失不可控。
- 本次重建即是这条决策的第一次执行：02 升到第 3 稿后，specs 随之重写，两者引用编号保持一一对应。

### 决策二：基线准入采用"达标才进"，并区分"落差"与"本期不包含"

一条需求进入基线，必须能指出代码中满足它的位置。做不到的，按性质分两类处理：

- **落差**：第 3 稿要求它、本期要交付，但代码未达标 → 登记到 `proposal.md` 落差表，留给后续独立 change，不进基线。
- **本期不包含**：第 3 稿已明确移出本期 → 不进基线，也不登记为落差，避免把"还没做"与"不打算做"混为一谈。

- 理由：`archive` 会把变更规格合并进 main specs。若把未达标的要求写进基线，合并之后 main specs 就在陈述未成立的事实，后续所有"specs 与代码不一致"的判断都会失真。
- 被否决的替代方案一：把 02 的全部功能点一次写成 specs（含未达标项），用 tasks 记录待修。否决理由是：`validate` 期间基线会长期趴着未达标要求，且落差与需求混在同一份文件里，无法区分"设计如此"与"尚未做到"。
- 被否决的替代方案二：先把 11 条落差修完再建基线。否决理由是：修落差需要先有需求口径，而口径的载体在 02 已就位、在 specs 尚未就位；先建基线能让每条落差的 change 都有一个干净的对照面。
- 已知代价：基线会明显比 02 窄（11 条落差 + 全部"本期不包含"项）。这是刻意取舍，落差表承担说明责任。

### 决策三：capability 按端划分，订单生命周期单独横切

capability 集合为 `customer-ordering`、`merchant-console`、`rider-delivery`、`platform-ops`、`ai-ordering-assistant`，加上横切的 `order-lifecycle`。

- 理由：前五个对应四个承载端与顾客端内的一个功能块，与 02 的功能结构一一对应，便于对照；订单状态集合与状态变更日志被多个端共同依赖，放进任一端都会造成重复声明。
- 被否决的替代方案：把订单处理拆到 `customer-orders` / `merchant-orders` / `rider-orders` 三个 capability。否决理由是同一批状态与日志会被声明三次，且状态机的整体性无法在一处读全。
- 被否决的替代方案：单独建 `role-auth` 承载四类角色的登录与令牌。否决理由是四类角色的认证方式与作用域规则各自不同（顾客为验证码、商户与骑手为账号密码、运营另需运营标识），抽成一层只会得到一个名词集合，各端的约束仍要分散声明。
- 边界说明：商户注册与入驻申请（F-B-01）、查看审核状态（F-B-03）本期要求但未达标，因此不归属任何 capability 的基线；平台侧的审核动作（F-D-02）已达标，归入 `platform-ops`。同一业务链路的两端落在不同能力里，是"达标才进"的必然结果。

### 决策四：规格语言与句式口径

需求语句统一使用中文的「系统应当……」，场景固定为 `**WHEN**` / `**THEN**` 两条，不引入第三条并列关键字。

- 理由：「系统应当」是中文语境下与 SHALL 等价的规定性表述。`openspec validate` 会对缺少英文 SHALL/MUST 的规格给出提示，该提示明确针对英文规格，本项目接受该提示，以 `validate` 通过为准，不使用 `--strict`。
- 被否决的替代方案：在中文句子里嵌英文 `SHALL`。否决理由是论文与规格面向中文读者，混排降低可读性。
- 场景不写第三条关键字：模板只约定 WHEN/THEN 两个关键字，额外关键字可能被解析器忽略，导致断言静默丢失；需要表达附加结果时并入 THEN。

### 决策五：基线对现状的"描述"优先于对需求的"复述"

当第 3 稿的表述比代码更宽时，基线写代码实际做到的那一层，并在该 capability 的 Purpose 下用一行说明指出差异所在。

- 例：`order-lifecycle` 写"骑手接单时记录归属、状态仍为待接单"，而不写第 3 稿的"接单即进入配送中"；`merchant-console` 直接说明 F-B-01 与 F-B-03 未纳入。
- 理由：规格的价值在于可验证。写进去的行为必须能通过观察验证；差异放进 Purpose 说明与落差表，能让读规格的人一眼看到"哪里还没跟上需求"，而不会误以为需求本身缩水了。

## Risks / Trade-offs

- [基线与 02 存在可见差距，可能被误读为需求被削减] → 落差表逐条登记差距、涉及的需求编号与后续归属；"本期不包含"与"落差"在提案中分列，避免两类东西混同。
- [落差表会随时间腐坏，修完一条却忘记更新] → 每条落差在后续 change 中消化时，同一 change 内同时更新落差表；把这一动作写进 `tasks.md` 的验收项。
- [02 与 specs 双向漂移] → 以 02 为唯一权威、specs 单向派生；`config.yaml` 的 context 已写明该方向，后续 change 若只改 specs 而不改 02，视为违反约定。02 从第 2 稿升到第 3 稿时，本 change 的重建即为一次实际的同步演练。
- [规格数量偏多导致维护成本] → 每个 requirement 只声明一种行为，场景只写可观察到的结果；不写实现细节，使规格不随重构而变。
- [基线不含规格维度，但代码里仍有 `product_spec` / `product_sku` 与遗留表] → 已在落差表登记为遗留物，由后续清理 change 处理；本 change 不触碰代码。
