# Design

## Context

与本 change 做法直接相关的现状：

- 商户端的认证装饰器是 `common/auth.py` 的 `merchant_login_required`：校验令牌、反查 `MerchantInfo`、把 `merchant` 注入 `request`，不检查 `status`。
- `merchant/api_views.py` 的 `login` 里有一行 `if merchant.status != 20: return fail_m('商户尚未通过审核，无法登录')`，是"用拒绝登录来实现经营门槛"的写法。
- `product/api_views.py` 与 `order/api_views.py` 的经营接口各挂 11 处 `merchant_login_required`，合计 22 处。
- 商户端前端只有登录页与登录后的布局，`router/index.ts` 的守卫只判断有没有令牌。
- `MerchantInfo.status` 的取值是 10 待审核 / 20 已通过 / 30 已驳回，此前只有 `STATUS_CHOICES`，没有具名常量。

## Goals / Non-Goals

**Goals:**

- 补齐 F-B-01、F-B-03 与 R3，使"商户自行入驻 → 平台审核 → 过审后才能经营"这条链路完整可演示。
- 让"未过审"的处置方式与需求一致：可以登录、只能看状态。
- 用一处校验覆盖全部经营接口，而不是在 22 个视图里各写一遍判断。

**Non-Goals:**

- 不做已驳回商户的重新提交或申诉流程。02 第 3 稿没有要求，R3 只说"只能查看入驻审核状态"。
- 不做商户资料的审核期间编辑。未过审期间资料不可改，避免出现"审核看到的是旧资料、商户改成了新资料"的错位。
- 不引入权限框架或角色表。本期商户只有"过审/未过审"两种经营权限状态，一个装饰器足够。

## Decisions

### 决策一：未过审的处理方式由"拒绝登录"改为"可登录 + 门禁"

登录对任何持有正确账号密码的商户开放，经营功能由单独的审核校验拦下。

- 理由：F-B-03 要求商户能查看审核状态，而"状态"只能通过登录后的身份获取。用拒绝登录来实现门槛，会让 F-B-03 在同一处被同时抹掉——这正是现状的问题。
- 被否决的替代方案：保留拒绝登录，另开一个免登录的"查询申请进度"接口。否决理由是那需要再造一套凭据（申请编号或手机号），等于把身份体系拆成两半，且与 UC-03「商户可登录并查看审核状态」的字面要求不符。

### 决策二：门禁放在装饰器层，新增 `merchant_approved_required`

在 `common/auth.py` 中与 `merchant_login_required` 并列新增一个装饰器：令牌无效返回 401，令牌有效但商户未过审返回 403 并带上当前状态；过审则与前者行为一致地注入 `request.merchant`。

- 理由：经营接口有 22 处，逐个视图写 `if merchant.status != ...` 会形成 22 份重复判断，任一处遗漏就是一个越权口子。装饰器把"是否过审"收敛成一处，与既有的"是否登录"保持同一层次。
- 返回 403 而不是 401：401 的语义是"身份未知"，会让前端跳登录页；这里是身份已知但权限不足，用 403 可以让前端把审核状态的提示直接展示出来。
- 被否决的替代方案：在 `merchant_login_required` 里直接加状态判断。否决理由是登录与查看状态本身也走这个装饰器，加了判断就会把它们一起挡掉。

### 决策三：注册的必填项为账号、密码、店铺名称、联系电话、店铺地址，店铺简介选填

- 理由：前五项是运营审核与顾客展示必需的信息；店铺简介是描述性内容，缺失不影响审核判断。UC-03 的异常流只要求"必填项缺失 → 拒绝提交并提示"，没有指定哪几项必填，这里按"审核是否能用得上"来划。
- 被否决的替代方案：把店铺简介也设为必填。否决理由是 F-B-01 的说明把它列为"入驻资料字段"，字段存在与字段必填是两回事，强制填写只会让演示时多一道无意义的卡点。

### 决策四：前端用路由守卫分流，审核状态做成独立页面

守卫读本地保存的审核状态：未登录去登录页，已登录但未过审只能停留在审核状态页，过审后自动放行到业务页。审核状态页在挂载时向服务端拉取一次最新状态。

- 理由：把"未过审能看什么"收敛到路由这一层，业务页面就不需要各自判断；同时未过审时业务菜单不会渲染，避免出现"点得进但全报错"的界面。
- 状态以服务端返回为准：本地缓存的状态只用于决定路由，页面展示与自动放行都以 `GET merchant/current` 的返回为准，审核通过后刷新即可进入，不需要重新登录。
- 被否决的替代方案：在布局组件里根据状态隐藏菜单项、不拦截路由。否决理由是那样业务页面仍可通过直接输入地址访问到，错误只会在接口返回 403 时才暴露。

### 决策五：未过审期间不允许修改店铺资料

`update_info` 与 `update_status`（营业状态）一并纳入门禁。

- 理由：R3 说的是"只能查看入驻审核状态"。若审核期间资料可改，运营看到的与商户提交的就会不一致。
- 权衡：商户发现资料填错时无法自行更正，只能等驳回后重新注册。这在 MVP 范围内可接受，已记录为 Not-Goals；若今后需要，再单独开放"审核期间的资料修正"。

### 决策六：状态取值用具名常量

`MerchantInfo` 上补 `STATUS_PENDING` / `STATUS_APPROVED` / `STATUS_REJECTED` 三个常量，`status` 字段默认值改用常量，装饰器与视图判断都引用常量。

- 理由：`20` 与 `MerchantInfo.STATUS_APPROVED` 相比，后者在装饰器与平台审核接口两处出现时不会读成魔法数字；取值不变，因此不产生迁移。
- 被否决的替代方案：保持字面量。否决理由是本次新增的判断集中在装饰器与前端守卫两处，常量能让"服务端的 20 与前端判定的 20 是同一件事"更容易核对。

## Risks / Trade-offs

- [注册接口是公开的，可能被批量注册] → 本期为毕设演示环境，未引入验证码或频率限制；注册会创建登录账号与商户记录，但状态恒为「待审核」，在通过平台审核前不具备任何经营能力，风险面被限制在"产生待审核记录"。
- [前端守卫依赖本地缓存的审核状态，可能与服务端不一致] → 本地状态只影响路由；真正执行经营操作时由服务端装饰器判定。缓存过期最坏情况是多跳一次审核状态页，不会产生越权。
- **[未过审商户不能再修改资料]** → 已在决策五记录取舍；若演示中需要，可现场由运营在后台修改该商户资料。
- [22 处装饰器替换是机械改动，有替换遗漏的风险] → 由测试覆盖：`test_pending_merchant_is_blocked_from_business_endpoints` 逐个命中菜品分类、菜品、订单、营业统计与店铺信息五类接口；若今后新增经营接口漏挂装饰器，该用例不会发现，因此把"新增经营接口必须挂 `merchant_approved_required`"作为约定记录在 `common/auth.py` 的装饰器文档串中。
