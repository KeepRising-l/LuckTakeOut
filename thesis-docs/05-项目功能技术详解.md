# 项目功能技术详解

**项目名称：** 基于 Python 的外卖平台的管理与实现（LuckTakeOut）

**文档定位：** 面向评审与答辩的技术说明——每个端、每个功能块**用到了什么技术、怎么实现、关键代码在哪里**，以及项目的技术亮点。

**版本：** 第 1 稿（2026-10-13）

---

## 一、技术栈总览

| 层次 | 技术 | 说明 |
| --- | --- | --- |
| 开发语言 | Python 3.12 | 后端；与课题"基于 Python"一致 |
| 后端框架 | **Django 6.1.2** | ORM、数据库迁移（19 个项目迁移文件，含 Django 内置迁移共 38 条迁移记录）、认证与权限、Admin 管理后台 |
| 数据库 | **SQLite**（默认，零配置）/ MySQL 8（`DB_ENGINE=mysql` 切换） | 金额字段全部使用 `Decimal` |
| 接口风格 | REST 风格 JSON，统一响应 `{code, info, data}` | 成功 `code='00000'` |
| 认证 | 基于 `django.core.signing` 的自签名 Token | 四类角色独立盐值，`Authorization: Bearer`，有效期 7 天 |
| AI 能力 | 大语言模型 **Function Calling**（OpenAI 兼容接口，默认硅基流动 DeepSeek 模型） | 手写 `urllib` 客户端（零第三方 SDK 依赖）+ 内置规则化 Mock 兜底 |
| 前端框架 | **Vue 3 + Vite + TypeScript** | 三端均为独立构建的单页应用（SPA） |
| 前端工程化 | **npm workspaces 单仓库多应用** | `apps/customer`、`apps/merchant`、`apps/rider` + `packages/shared` |
| 前端组件库 | **Vant 4**（顾客端、骑手端）、**Element Plus + ECharts**（商户端） | 移动端组件库与桌面后台组件库分别选型 |
| 前端状态与路由 | Pinia + Vue Router | 三端各自维护状态与路由 |
| HTTP 客户端 | axios（统一封装于共享包） | ResultAPI 解包、401 自动跳登录、按端注入 token |
| 运营端 | Django Admin | 商户审核、全局查询、骑手账号维护、操作日志 |
| 测试 | Django Test（Python unittest） | 101 项测试全绿，覆盖越权、状态迁移、口径与入驻链路 |
| 工程规格 | OpenSpec（spec-driven 工作流） | 需求投影为 6 个 capability / 50 条可验收要求 |

**依赖极简主义：** 后端生产依赖仅 `Django` 一项（`requirements.txt` 只有一行；MySQL 切换时加 `mysqlclient`），AI 调用用标准库 `urllib` 手写 HTTP——没有 LangChain 之类的重框架。所有机制（认证、状态机、工具调用循环）都在项目代码内可见、可读、可答辩。

## 二、系统架构

```
┌────────────────────────────────────────────────────────────────┐
│  表现层                                                          │
│  ┌──────────┐ ┌──────────┐ ┌──────────┐ ┌──────────────────┐   │
│  │ 顾客端 SPA │ │ 商户端 SPA │ │ 骑手端 SPA │ │ 运营端(Django    │   │
│  │ Vant 4    │ │ Element+ │ │ Vant 4    │ │ Admin)           │   │
│  │ 13 个页面  │ │ ECharts  │ │ 4 个页面  │ │                 │   │
│  └────┬─────┘ └────┬─────┘ └────┬─────┘ └────────┬─────────┘   │
│       └───────┬────┴───────┬────┘                │              │
│          packages/shared（请求封装·token·状态文案）│              │
├───────────────┼────────────┼─────────────────────┼──────────────┤
│  接口层（Django 函数视图 + 统一响应）              │              │
│  /api/v1/* 顾客端  /api/* 商户端·骑手端·运营端    │              │
│  认证装饰器 · 作用域过滤 · 参数校验                │              │
│  ┌───────────────────────────────────────┐       │              │
│  │ AI 工具接口（ai_service.tools）9 个    │       │              │
│  │ ※ 与人工接口共用同一套认证与作用域      │       │              │
│  └───────────────────────────────────────┘       │              │
├───────────────────────────────────────────────────┼──────────────┤
│  数据层（Django ORM）                              │              │
│  20 张业务表 · 订单状态机（order/state.py）· 审计日志           │
│  SQLite（默认）/ MySQL 8（可切换）                 │              │
└──────────────────────────────────────────────────────────────────┘
```

**架构要点：**

1. **前后端分离 + 同源托管**：前端三端各自构建出 `dist`，由 Django 的 `spa_serve` 视图同源托管（顾客端在 `/`、商户端 `/merchant/`、骑手端 `/rider/`），命中文件返回文件、未命中回退 `index.html`（SPA 路由）；`/assets/*` 与 `/<端>/assets/*` 由 `spa_asset` 依次到三端 `dist/assets` 查找、找不到直接 404（不回退 HTML，避免浏览器把 HTML 当 JS/CSS 解析）。商户端用 hash 路由、骑手端也用 hash 路由，顾客端商家详情页占 `/shop/:id`，不与 `/merchant/` 挂载前缀冲突。单端口（8091）即可完成全端演示，无跨域、无 nginx。
2. **AI 与业务解耦**：AI 服务（`ai_service`）只通过工具接口参与业务，不直接操作数据库；工具与人工请求共用同一套安全机制。
3. **不设 Service 层**：视图函数直接使用 ORM，以两条硬性约定替代抽象层——认证统一用 `common/auth.py` 的装饰器；涉及资源的查询一律带作用域条件（`user` / `merchant` / `rider`）。

## 三、四端功能与技术实现

### 3.1 顾客端（H5，13 个页面）

| 功能块 | 技术实现 |
| --- | --- |
| 手机号 + 验证码登录 | Django 认证体系 + 自签名 token；演示环境验证码直接返回（`/api/v1/auth/code`），任意手机号 + `123456` 可登录 |
| 商户列表 / 搜索 | 商户列表接口只返回**已通过审核**的商户，支持按商户名称关键词筛选；只展示名称、简介、评分（评价均值的真实计算）、配送费（平台固定 2 元）；不含销量与距离。搜索页同时查商户名与菜品名（`/merchants/nearby` + `/products/search` 并集去重），命中菜名时给出其所属商户 |
| 点菜与购物车 | 购物车由**前端状态（Pinia）+ localStorage** 维护，不落库；跨页数据一致由 store 保证 |
| 下单与支付 | 订单金额由**服务端重算**（`pay_amount = 商品合计 + 配送费`，忽略客户端传值）；模拟支付写 `payment_record`；下单校验收货地址归属 |
| 订单列表与详情 | 状态取值直接使用后端整数枚举（10-60），文案由 `packages/shared/orderStatus.ts` 按顾客视角呈现 |
| 取消订单 | 仅"待支付"或"已支付且未被接单"可取消；经状态机校验 |
| 地址管理 | 新增 / 删除 / 默认地址；后端校验地址归属（本人） |
| 评价 | 一单一评，仅已完成订单可评（后端在创建时校验状态与重复） |
| **AI 点餐助手** | 独立页面 `AiChat.vue`：会话创建 → 多轮对话 → 草稿卡片展示 → 确认转正式订单（详见 3.5） |

### 3.2 商户端（桌面后台，8 个页面）

| 功能块 | 技术实现 |
| --- | --- |
| 注册与入驻 | `Register.vue`：一步完成注册 + 提交入驻资料（账号、密码、店名、电话、地址、简介）→ 生成"待审核"商户 |
| 审核状态 | `ReviewStatus.vue`：未过审商户登录后只能看到审核状态页（后端以 `merchant_approved_required` 拒绝其余经营接口，403） |
| 登录 | 账号 + 密码，签发商户专属盐值 token |
| 分类 / 菜品管理 | 常规 CRUD + 上下架 + 可售数量调整；所有查询带 `merchant=` 作用域 |
| 订单处理 | 接单（已支付 → 待接单）、取消；订单的完成由骑手送达确认触发（配送中 → 已完成）。状态变更全部经 `change_status()` |
| 营业统计 | `Dashboard.vue`：**ECharts** 绘制营收趋势（7 天）与热销菜品 Top10，数据由后端按本店真实数据聚合 |
| 店铺信息 | 名称、简介、地址、电话、门店图片上传（Django media） |

### 3.3 骑手端（H5，4 个页面）

| 功能块 | 技术实现 |
| --- | --- |
| 登录 | 账号 + 密码（账号由平台运营创建），骑手专属盐值 token；9 个配送接口全部鉴权，跨骑手操作 403 |
| 工作台 | 上下线状态、待抢单池（状态 30 且无骑手的订单）、今日完成单数；任务状态是由订单状态 + 骑手归属**派生的视图状态**（待抢单/已接单/配送中/已完成），非订单状态本身 |
| 接单 | 抢单即进入"配送中"（不设"取餐中"中间态）；记录 `rider` 归属 |
| 送达 | 配送中 → 已完成，记录 `deliver_time` |
| 任务详情 / 个人页 | 本人任务列表（进行中、已完成） |

### 3.4 平台运营端（Django Admin）

| 功能块 | 技术实现 |
| --- | --- |
| 商户入驻审核 | Admin 自定义 action：通过 / 驳回，**审核写操作日志** |
| 商户 / 顾客 / 订单查询 | Admin 列表页 + 过滤器 + 搜索框 |
| 骑手账号维护 | Admin 创建骑手及其登录账号 |
| 平台统计 | 商户数、待审核数、顾客数、订单数、营业额 |
| 操作日志 | `operation_log`（含 AI 工具调用记录，`actor_role='ai'`）与站内信 |

> 运营端由 Django Admin 承载，是 4.2 节"选 Django 的理由 1"的兑现场景；接口层另有 `/api/platform/*` 供后续自研前端替换（已加 `is_staff` 校验）。

### 3.5 AI 点餐助手（核心功能，全链路）

**技术链路：**

```
顾客消息 → agent.run_agent()（多轮循环，MAX_STEPS=8）
   │
   ├─ llm.chat_completion(messages, tools=TOOL_SCHEMAS)
   │     有 LLM_API_KEY → urllib 调用 OpenAI 兼容 /chat/completions（temperature=0.2）
   │     无 Key（或答辩断网）→ 内置规则化 Mock（按关键词驱动下单/催单/评价三条链路）
   │
   ├─ 模型返回 tool_calls → tools.execute_tool() 本地执行
   │     search_merchant / search_menu / validate_draft / create_draft /
   │     get_order_status / urge_order / submit_review /
   │     get_my_history / recommend_dishes
   │     每次执行写 operation_log（actor_role='ai'）
   │
   └─ 循环直到模型输出文本回复 → 写入 chat_message
```

**关键实现点：**

| 点 | 实现 |
| --- | --- |
| 工具定义 | 9 个工具以 OpenAI 兼容 JSON Schema 声明（`tools.py` 的 `TOOL_SCHEMAS`），模型只"理解与组织参数" |
| 后端重校验 | `validate_draft` 以数据库中价格、库存、商户归属为准重算，任何模型幻觉在进入草稿前被拦截 |
| 草稿机制 | `create_draft` 只写 `order_draft` / `order_draft_item`（含价格快照），不产生正式订单；顾客在前端确认后由服务端转正式订单 |
| 系统提示词 | `agent.py` 的 `SYSTEM_PROMPT` 规定 7 条硬规则（只能通过工具获取信息、不得编造价格、下单必走四步等） |
| 会话持久化 | `chat_session` / `chat_message`（角色含 user/assistant/tool 与工具名），支持历史回溯 |
| 催单 | `urge_order` 写 `urge_record` + 向商户/骑手写站内信 |
| 作用域 | 会话、消息、草稿、订单全部以**登录顾客**为作用域（`_current_customer()` 从 token 反查，不读请求体） |
| 画像推荐与复购 | `recommend.py` 生成口味画像（常点商户/菜品、客单价、常点时段）；首页「猜你想吃」按历史推荐并带理由，`GET /api/v1/ai/recommend` 输出画像 + 推荐列表；「再点一单」由 `POST /api/v1/ai/reorder` 按最近订单重建草稿，自动跳过下架/缺货菜品；确认草稿即完成支付（前端串联支付接口，不经购物车） |
| Mock 兜底 | `llm.py` 内置规则化实现：识别"催/评价/下单"意图，按序模拟工具调用链，**答辩现场不配 Key 也能完整演示** |

## 四、核心机制详解

### 4.1 统一响应与请求分发

- **结果格式**：所有接口返回 `{code, info, data}`，成功 `code='00000'`；`common/response.py` 提供 `ok()` / `fail()`。
- **方法分发**：`common/dispatch.py` 的 `by_method(GET=..., POST=...)` 让同一路径的不同方法路由到不同处理函数（如 `addresses`、`orders`）。
- **CSRF 豁免**：`common.middleware.ApiCsrfExemptMiddleware` 对 `/api` 前缀豁免 CSRF（令牌认证的无状态接口不需要 CSRF token），Admin 页面仍受 CSRF 保护。
- **CORS**：`common.middleware.CorsMiddleware` 支持前端开发态（5173-5175）跨端口联调。

### 4.2 认证体系（四类角色、独立盐值）

```
make_token / make_merchant_token / make_rider_token / make_platform_token
   └─ django.core.signing.dumps({'uid': ...}, salt=<每端独立>)
请求头 Authorization: Bearer <token> → 验签 + 过期校验（7 天）→ 反查 User
装饰器：
   api_login_required         顾客端（兼 AI 接口）
   merchant_login_required    商户登录（仅 login / current）
   merchant_approved_required 商户经营接口（登录 + 过审双重门槛）
   rider_login_required       骑手端
   platform_login_required    运营端（额外要求 is_staff）
```

**设计价值**：独立盐值使四类凭证互不通用（结构性隔离）；装饰器使"每个接口的权限门槛"在路由文件里一眼可见、可审计。

### 4.3 数据隔离与越权防范

- 商户端：所有经营接口经装饰器注入 `request.merchant`，查询一律带 `merchant=` 过滤；
- 顾客端：订单、地址、草稿、会话以 `user=` / `customer=` 过滤；
- 骑手端：任务以 `rider=` 过滤，跨骑手操作返回 403；
- AI 侧：所有工具在会话顾客的作用域内执行，模型无法指定他人身份。
- **测试证据**：101 项测试中包含专门的越权用例（跨商户访问、跨顾客访问、跨骑手操作）。

### 4.4 订单状态机

```
ALLOWED_TRANSITIONS = {
  10 待支付 → {20 已支付, 60 已取消}
  20 已支付 → {30 待接单, 60 已取消}
  30 待接单 → {40 配送中, 60 已取消}
  40 配送中 → {50 已完成}
  50 已完成 → {}          60 已取消 → {}
}
change_status(order, to_status, operator_role, operator_id, **fields)
```

- 单一入口 `order/state.py::change_status()`：校验迁移合法性 → 落库 → 写 `order_status_log`（原状态、新状态、操作者角色、时间）；
- **非法迁移被拒绝且不写日志**；状态未变化视为成功且不写日志；
- 商户端可提交的目标状态有白名单（`MERCHANT_TARGET_STATUSES`），是对外契约的一部分；
- 顾客支付/取消、商户接单/完成/取消、骑手接单/送达全部走此入口，无旁路。

### 4.5 前端工程化

- **monorepo**：`web/` 下 npm workspaces，`packages/shared` 提供 `request.ts`（axios 拦截器：ResultAPI 解包、401 跳对应端登录、按端注入 token）、`storage.ts`、`format.ts`、`orderStatus.ts`（状态文案表）；
- **三端构建**：`npm run build` 依次构建三端 `dist`；开发态 `run-dev.bat` 一次启动三个 Vite 服务（5173/5174/5175，`/api` 代理到 8091）；
- **同源托管**：Django `spa_serve` 按前缀托管三端产物；构建产物缺失时返回明确的 404 提示（旧版静态页已于 2026-10-13 移除，不再提供回退）。

### 4.6 审计日志

- `operation_log` 记录：操作者（`actor_id` + `actor_role`，含 `ai`）、动作、目标、参数与前后状态（detail）、结果（success/fail）、时间；
- 覆盖：商户审核、AI 工具调用（9 个工具全部）、草稿创建/确认、退款闭环（申请/审核/拒绝/越权）、
  库存扣减与取消回补、评价约束、登录与地址作用域、关键订单操作；
- 修复记录：早期 AI 审计因取一个恒为空的字段而恒空，已修复为写入真实操作者标识。

## 五、项目亮点（答辩提炼）

| # | 亮点 | 一句话说明 | 证据锚点 |
| --- | --- | --- | --- |
| 1 | **受控的 AI 下单** | 模型只生成待确认草稿；价格/库存/归属由后端重校验；顾客确认后才产生正式订单 | `ai_service/tools.py`、`views.py` |
| 2 | **AI 无特权通道** | AI 工具与人工接口共用同一套认证与作用域；无免认证入口；全程审计 | `ai_service/views.py`、`tools.py` 的 `_audit()` |
| 3 | **订单状态机单一真值** | 合法迁移表 + 单一变更入口 + 状态日志；非法迁移被拒 | `order/state.py` |
| 4 | **四类角色独立盐值认证** | 基于 Django signing，零额外依赖；凭证互不通用 | `common/auth.py` |
| 5 | **多商户治理闭环** | 注册即申请入驻 → 平台审核 → 未过审禁止经营（27 处接口统一门槛） | `merchant_approved_required` |
| 6 | **口径统一机制** | 订单状态整数唯一真值、文案集中共享包；配送费服务端重算快照入库 | `packages/shared/orderStatus.ts`、`order` 模块 |
| 7 | **可复现的工程化** | 50 条可验收要求驱动实现；101 项测试全绿；OpenSpec 规格体系 | `openspec/`、`manage.py test` |
| 8 | **演示鲁棒性** | LLM 客户端零依赖手写 + 内置 Mock，**断网/无 Key 也能完整演示 AI 链路** | `ai_service/llm.py` |
| 9 | **单端口同源演示** | 三端构建产物由 Django 托管，答辩换机只需三个命令 | `config/urls.py` 的 `spa_serve` |
