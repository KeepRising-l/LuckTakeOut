# 答辩应对问答

**项目名称：** 基于 Python 的外卖平台的管理与实现（LuckTakeOut）

**使用说明：** 按"评委可能提问的方向"分为七类。每题给出**回答骨架**（答辩时可展开成 30 秒~1 分钟的口述）与**追问预案**（评委继续挖时的准备）。回答均基于项目的真实实现，对应代码位置见 `05-项目功能技术详解.md` 第六章。

**版本：** 第 1 稿（2026-10-13）

## 一、选题与立意

### Q1. 为什么选择做外卖平台？这个课题的意义是什么？

**回答骨架：**
外卖平台是多商户系统的典型形态——"一个平台、多方参与"，天然包含入驻审核、数据隔离、交易流转这些有分量的工程问题，适合作为"完整业务系统"的毕设载体。同时我在此基础上叠加了一个有研究性的问题：**大语言模型如何安全地参与业务系统**。美团、饿了么这类平台的研究价值在于商业调度，而我关注的是另一个点——模型输出不可信时，业务系统应该怎么设计才能既用上 AI、又不被 AI 搞坏数据。这是课题的立意。

### Q2. 你的项目跟网上的开源外卖项目有什么区别？

**回答骨架：** 三点区别：
1. 多数开源外卖/点餐项目是**单商户**的（一家店自己点餐），没有平台方、审核与多租户隔离；我实现的是真正的多商户——注册即入驻申请、平台审核、未过审不能经营、商户间数据隔离；
2. 我的 AI 点餐是**受控设计**：模型只生成待确认草稿，价格库存由后端重校验，模型永远碰不到正式订单的写入口；套壳 AI 的常见做法是模型直接调接口写数据，出了问题不可控；
3. 工程治理完整：51 条可验收要求、106 项自动化测试、需求文档与实现对齐，这些是可验证的。

### Q3. 这个项目是你自己做的吗？工作量怎么体现？

**回答骨架：** 项目从需求收敛、规格拆解、编码、测试到文档是完整走通的：后端 11 个业务模块、20 张业务表、19 个项目迁移（连同 Django 内置迁移共 38 条迁移记录）；前端三个独立应用共 25 个页面；后端 106 项测试全绿。需求文档有五稿演进，第 4 稿按"最小可行范围"收敛、第 5 稿落实退款；规格体系（OpenSpec）把需求投影成 51 条可验收条目；演进中发现并修复了 8 类真实问题（AI 接口无认证、订单越权、状态脏迁移、骑手可冒名操作等），这些修复都有对应的测试。工作量主要体现在"从需求到可验收实现"的完整链路，这一点材料里都可以查证。

### Q4. 你的创新点是什么？

**回答骨架（四条）：**
1. **可控的对话式下单**：AI 只生成"待确认订单草稿"，真实下单必须经后端重校验与顾客确认——模型输出永远不直接落库；
2. **AI 操作可审计**：10 个工具调用全部写操作日志（`actor_role='ai'`），可追溯"AI 何时以什么参数做了什么"；
3. **AI 与业务共用同一套安全边界**：AI 调用的接口与人工请求走同一套认证、作用域校验和业务规则，AI 没有任何特权通道；
4. **可量化的评估**：定义了槽位字段准确率、下单耗时对比、非法请求拦截率三个指标——AI 功能好不好，用数据说话。

## 二、技术选型

### Q5. 为什么用 Django 不用 FastAPI / Spring Boot？

**回答骨架：** 四条理由：
1. **运营端直接复用 Django Admin**：平台运营端（商户审核、全局查询、操作日志）不用写前端就获得了完整的后台，这是多商户平台不可缺少的一环；FastAPI 需要自己造或接组件；
2. **ORM 与迁移一体化**：20 张业务表、19 个项目迁移由同一套体系管理；FastAPI 需要自行组合 SQLAlchemy + Alembic；
3. **认证体系可直接复用**：四类角色建立在 `django.contrib.auth` 之上；
4. **性能不在本课题的痛点上**：教学演示规模，吞吐量不是瓶颈，而 FastAPI 的异步高并发优势体现不出来。
（如果被问 Spring Boot：那是我 Java 技术栈的方向，本课题定位于 Python，且 Django 的"电池全含"特性正好匹配"单人完成全栈"的规模。）

### Q6. 为什么用 SQLite？能支撑真实业务吗？

**回答骨架：** SQLite 是**演示与开发的默认**，为了"零配置、换机即跑"——答辩现场拿一台装了 Python 的电脑就能演示。但设计上没有绑定 SQLite：通过环境变量 `DB_ENGINE=mysql` 一键切换到 MySQL 8，连接参数全部外置（host/port/name/user/password）。金额字段全部用 `Decimal`，迁移体系对两种数据库都通用。真实生产当然用 MySQL/PostgreSQL 并关闭 DEBUG，这点在文档里是明确说明的。

### Q7. 前端为什么用 Vue？为什么三个端要分开？

**回答骨架：** 三端的分开是**交互形态差异**决定的：顾客端和骑手端是移动端 H5（用 Vant 4），商户端是桌面后台（用 Element Plus + ECharts），共用一套页面代码会互相牵制。但三端对后端的契约是同一套，所以我用 npm workspaces 做了单仓库多应用：三个应用独立构建，共用一个 `packages/shared` 包——请求封装（axios 拦截器、401 跳转、token 注入）、格式化、**订单状态文案表**全部下沉共享，保证三端对同一个订单状态的取值和口径绝不漂移。构建产物由 Django 同源托管，单端口即可演示全部三端。

### Q8. 为什么不用 DRF（Django REST Framework）？为什么不用 Redis、消息队列、微服务？

**回答骨架：** **规模匹配原则。**教学规模（单机、数十接口级别）下，每个额外的技术组件都要用一套口径去解释和维护：DRF 的序列化器和视图集抽象会让"一个接口从头到尾发生什么"变得不直观，我选择手写函数视图 + 统一响应封装，让权限、作用域、业务逻辑在一个文件里一眼可见；Redis/消息队列/微服务解决的是高并发、解耦与独立伸缩问题，我当前没有这些流量与团队规模的痛点，引入反而是负分。**取舍的依据是"这个组件解决了什么这是我的瓶颈的问题"**——答不出这一句的组件就不该引入。

## 三、AI 与创新点（重点准备）

### Q9. AI 点餐是怎么实现的？技术链路讲一下。

**回答骨架：** 链路是：
1. 顾客在顾客端打开助手，后端以**登录顾客**为作用域创建会话；
2. 顾客用自然语言表达需求，后端调用大语言模型（OpenAI 兼容的 Chat Completions 接口 + Function Calling），系统提示词约束模型"只能通过工具获取信息、不得编造价格"；
3. 模型按需调用 10 个后端工具：搜索商户、查菜单、校验草稿、生成草稿、查订单状态、申请退款、催单、提交评价、查口味画像、按偏好推荐菜品——**工具在后端执行**，模型只负责组织参数；
4. 下单场景下模型依次走四步：`search_merchant` → `search_menu` → `validate_draft`（后端重校验）→ `create_draft`（生成待确认草稿）；
5. 草稿在前端展示，顾客点确认后，**服务端**把草稿转为正式订单（待支付）；每次工具调用和草稿操作都写审计日志。

### Q10. 模型幻觉怎么办？它乱报价格、乱加购物车怎么防止？

**回答骨架：** 我的设计是让幻觉**没有生效路径**：模型输出的价格、库存、商户归属从来不被信任，`validate_draft` 工具以数据库现状重新计算每一项价格与可售数量，校验不过就返回错误让模型向顾客解释；就算模型组织出错误的参数，最终生成的也只是"草稿"，价格以服务端校验结果为准；正式订单必须顾客在前端明示确认后才由服务端创建。所以模型能造成的最坏结果是"草稿内容不对"，顾客一看价格不对就不会确认——而它永远无法直接写库、无法发起支付。

### Q11. 为什么让 AI"调工具"，不让它直接生成订单文本再解析？

**回答骨架：** Function Calling 是当前工业界的标准做法，优势有三：1）模型输出的参数是**结构化 JSON Schema**（比如 `merchant_id: integer`），不用自己写脆弱的文本解析；2）工具由后端定义与执行，模型只能在**允许的动作集合**里选择，"能做什么"是我控制的；3）每次调用天然可以记录审计（工具名 + 参数）。相比"让模型生成一段文本再解析"，出错面小得多。

### Q12. 缺信息、歧义、顾客改口这些情况怎么处理？

**回答骨架：** 分两层：提示词层，系统提示词明确"商户找不到就请顾客澄清、菜品下架就给候选"；程序层，`search_merchant` 支持关键词模糊搜索（名称/简介），找不到返回空列表让模型组织澄清话术；地址未提供时用该顾客的默认地址；订单查询未指定单号时取最近一笔订单。对话完整落库（`chat_session` / `chat_message`，含工具消息），可以回溯每一轮的上下文。**诚实补充**：多轮槽位状态的显式建模（比如把"已收集到哪些槽位"作为结构化状态管理）是当前实现可以加强的地方，目前依赖提示词 + 工具返回驱动。

### Q13. 网络断了 / 模型服务挂了，演示怎么办？

**回答骨架：** 有内置的规则化 Mock 兜底：LLM 客户端检测到未配置 API Key 时，自动切换到本地规则实现——按关键词识别"下单/催单/评价"三条链路，模拟同样的工具调用序列并生成回复。所以**答辩现场不配 Key、不联网也能完整演示 AI 下单链路**。配置真实模型时只是把 `LLM_API_KEY` 通过环境变量注入（`run.bat` 从本地的 `llm_key.txt` 读取，该文件不入库）。

### Q14. 为什么不用 LangChain 之类的框架？

**回答骨架：** 规模与透明度优先。我的工具调用循环（消息构建 → 模型调用 → 工具执行 → 结果回填 → 循环）总共约 70 行代码，用标准库 `urllib` 手写 HTTP，**后端生产依赖只有 Django 一项**。引入 LangChain 会增加一层我需要解释的黑盒，而它解决的编排复杂度（多模型、多记忆后端、复杂链）在我的规模下并不存在。这个选择的原则和 Q8 一致：组件的收益必须对应我的真实痛点。

### Q15. 用的什么模型？成本如何？

**回答骨架：** 默认接 OpenAI 兼容接口（默认模型 `deepseek-v4.1-flash`，经 rayagent 中转），配置项（`LLM_BASE_URL` / `LLM_MODEL` / `LLM_API_KEY`）全部外置可换，硅基流动等任意兼容服务都能直接替换。演示规模下每次下单约 4-5 次模型调用，对话历史截断到最近 20 条控制上下文长度。成本可控，且断网有 Mock 兜底。

## 四、安全

### Q16. 怎么防止越权？数据隔离怎么做的？

**回答骨架：** 核心原则是"**作用域只从登录态取，不信任请求参数**"。商户端所有经营接口经过装饰器注入 `request.merchant`，查询一律带 `merchant=` 过滤；顾客的订单/地址/草稿/会话以登录顾客过滤；骑手的任务以本人 `rider=` 过滤；AI 工具执行时也限定在会话顾客的作用域内。另外我**用测试证明**：106 项测试里有专门的越权用例——跨商户访问、跨顾客访问、跨骑手操作，全部要求被 403/404 拦截。举一个真实修复的例子：早期订单详情接口没有归属校验，任何登录用户改一下订单 ID 就能看别人的订单，这个洞是查出来并修掉的——这是"接口逐个过安全审查"的产物。

### Q17. 认证怎么做的？为什么不用 JWT？

**回答骨架：** 用 Django 自带的签名机制（`django.core.signing`）自签 token：载荷是用户 ID，有效期 7 天，请求头 `Bearer` 携带。选择它的理由：1）零额外依赖（不引 JWT 库）；2）**四类角色（顾客/商户/骑手/运营）使用独立盐值**——商户端的 token 拿到顾客端验签直接失败，凭证互不通用，这比"一个 token 里判断角色字段"多一层结构性防护；3）运营端额外校验 `is_staff`。相比 Session 的好处是无状态、前后端分离下天然适配。局限也诚实说明：无法主动吊销单个 token（教学规模可接受）。

### Q18. 订单状态被乱改怎么办？比如把配送中改回待接单。

**回答骨架：** 改不了。订单状态 10-60 六个取值，**所有变更必须走 `order/state.py` 的 `change_status()`**：先查合法迁移表——比如配送中（40）的合法去向只有已完成（50），想改回 30 会被拒绝；通过后落库**并写状态变更日志**（原状态、新状态、操作者、时间）；非法迁移被拒绝且不写日志。顾客支付/取消、商户接单/完成/取消、骑手接单/送达全部走这个入口，没有任何旁路直接改 `status` 字段。测试里有针对合法与非法迁移的专项用例。

### Q19. 密钥怎么管理的？（诚实题）

**回答骨架：** 分两层：LLM 的 API Key 通过环境变量注入（本地放在 `llm_key.txt`，已被 gitignore，从不入库）；Django 的运行配置同样支持环境变量注入——`SECRET_KEY`、`DEBUG`、`ALLOWED_HOSTS` 三项均可由环境变量覆盖（`DJANGO_SECRET_KEY` / `DJANGO_DEBUG` / `DJANGO_ALLOWED_HOSTS`），开发与演示模式使用内置默认值保持零配置，**生产模式（`DJANGO_DEBUG=0`）下未注入密钥会直接拒绝启动**，避免带默认密钥上线。token 的盐值（salt）属于公开的命名空间标识，四端凭证的安全性锚定在 `SECRET_KEY` 上，这一点在设计时是明确的。

## 五、工程与测试

### Q20. 测试怎么做的？覆盖了什么？

**回答骨架：** 后端 106 项自动化测试（Django Test），当前全绿。覆盖五类：作用域越权（跨商户/跨顾客/跨骑手）、订单状态迁移合法性（合法放行 + 非法拦截）、业务口径（配送费固定值且服务端重算、下单扣减库存与取消回补、假值清理后的展示字段）、商户入驻链路（注册→审核→过审前 403→过审后放行）、AI 链路（工具执行与草稿确认）。另外交付前跑过全链路手工 E2E：下单 → 支付 → 商户接单 → 骑手配送 → 顾客评价。

### Q21. 需求是怎么变成实现的？会不会做着做着跑偏？

**回答骨架：** 用了 OpenSpec 的规格驱动流程：需求文档（第 4 稿）先收敛范围 → 规格体系把需求投影成 6 个功能域、**51 条可验收要求**（每条都有 WHEN/THEN 场景，机器可校验"是否丢掉场景"）→ 实现对着规格做 → 差距登记在提案里逐条消化。过程中还建立了"基线只写代码已达标的规格"的纪律，已承诺未达标的进落差表跟踪——最终 11 条落差全部消化归零。这套机制保证了"文档说的就是代码做的"。

### Q22. 做过性能考虑吗？

**回答骨架：** 在课题规模下定位是"功能性正确性优先"，但也做了基础措施：订单与状态日志建了组合索引（`order_info(user, status)`、`order_info(merchant, status)`）；支付等关键操作使用数据库事务保证一致性；AI 对话历史截断（20 条）控制上下文成本。没有做缓存层与异步，因为教学演示规模下不是瓶颈——如果被问到真实高并发场景，我清楚在哪里扩展（缓存、任务队列、读写分离）。

## 六、不足与展望（必问题）

### Q23. 你觉得项目有什么不足？

**回答骨架（主动暴露，显示清醒）：**
1. 平台运营端目前由 Django Admin 承载，功能完整但界面是 Admin 的通用风格；自研前端的后端接口已经备好，属于可继续完善项；
2. 默认运行配置是演示取向（SQLite、Django 本地文件存储），正式生产需切换 MySQL 与专业部署方式（切换机制与部署文档已就绪）；
3. 库存策略是"校验不扣减"，并发下单场景下可售数量的语义是"软约束"——这是有意的口径收敛，不是遗漏；
4. AI 的槽位管理依赖提示词 + 工具返回驱动，没有做显式的多轮槽位状态机，复杂改口场景的可控性还可以加强。

### Q24. 如果继续做，下一步做什么？

**回答骨架：** 按价值排序：1）运营端自研前端（接口已就绪）；2）AI 槽位状态显式化 + 评估数据集固化（把论文里的三个指标做成可重复跑的评测脚本）；3）退款流程（已纳入规划：需求稿已收录、订单状态枚举已预留"退款中/已退款"，实现时同步补数据表、接口、测试与规格）；4）正式部署落地（MySQL + 反向代理 + 应用服务器；密钥注入与 DEBUG 关闭机制已就绪）。

### Q25. 退款、真实支付、地图配送为什么不在本期范围？

**回答骨架：** 本期范围收敛的标准是三问：砍掉后三条主线（交易闭环、受控 AI、多商户证据）是否仍自洽？是否引入新口径需要额外解释？是否引入新的数据依赖？真实支付与地图配送引入的是"第二套口径"，因此先保证主线做深。**退款原本按此逻辑列为后期实现项，现已实现**——顾客对已支付/待接单订单申请全额退款 → 商户审核（同意则模拟到账、订单「已退款」，拒绝退回申请前状态）→ `refund_record` 留存全程，状态机开通 70/80 并有配套测试兜住"退款中不可被取消/接单"等约束；真实支付需要第三方资质与回调处理、地图配送需要地图服务与调度算法，仍不纳入。**明确不做什么、并说清为什么，和不做什么都不知道，是两回事。**

## 七、演示与实操

### Q26. 现场演示怎么安排？

**回答骨架：** 演示路径（约 3 分钟）：后端点 `run.bat` 启动（未配 Key 会自动走 Mock，**先声明这是为了演示稳定的设计**）→ 顾客端下单支付 → 商户端接单（可以展示审核状态页证明入驻链路）→ 骑手端抢单送达 → 顾客评价 → 最后演示 AI 助手对话式下单（展示草稿 + 确认）→ 补一句"后台的操作日志里能看到刚才 AI 的每一步工具调用"（这段最有说服力）。

### Q27. 演示失败了怎么办？

**回答骨架：** 三层兜底：1）AI 链路有 Mock（断网/无 Key 照常演示）；2）数据层：`seed_demo` 命令可随时重建演示数据（商户、菜品、骑手、顾客）；3）最坏情况用预先准备的操作录屏或分步截图讲解。任何一层失效都有退路，不会出现"卡死讲不下去"。
