## 一、引言

### 1.1 编写目的

本文档用于明确"基于 Python 的外卖平台"的功能需求与非功能需求，作为系统设计、编码实现与测试验收的依据。预期读者为开发者、指导教师与评审人员。

### 1.2 项目背景

本系统是一个**多商户**外卖平台：平台作为运营方，接入并审核多个入驻商户；商户各自维护菜品与订单；骑手负责配送；消费者在平台内浏览、下单、支付与评价。在此基础上，顾客端内置一个**AI 点餐助手**，借助大语言模型的函数调用能力，为顾客提供对话式的辅助服务（下单、催单、评价）。AI 能力以顾客端的一个功能形态存在，可用可不用，不改变顾客端既有交易流程，也不引入新的角色。

### 1.3 术语与定义

| 术语 | 含义 |
| --- | --- |
| 商户（Merchant） | 入驻平台的餐饮商家 |
| 顾客（Customer） | 下单的终端消费者 |
| 骑手（Rider） | 负责订单配送的配送人员 |
| 平台运营（Admin） | 平台的运营管理人员，负责商户审核与全局管理 |
| AI 点餐助手 | 顾客端内置的对话式辅助功能，由大语言模型驱动，通过后端工具接口参与业务 |
| 草稿单（Order Draft） | AI 辅助生成的、尚未确认的待下单内容，不产生真实交易 |
| 槽位（Slot） | 下单所需的结构化字段：商户、菜品、数量、地址 |
| 越权 | 用户访问了不属于自己权限范围的数据或功能 |

### 1.4 角色口径说明

本系统共 **四类角色**：顾客、商户、骑手、平台运营。AI 点餐助手是顾客端内的一个功能，**不构成独立角色，也不单独成端**：它代表当前登录的顾客发起操作，操作主体、权限边界与作用域均归属该顾客。

## 二、系统概述

### 2.1 系统目标

实现一个可运行的多商户外卖平台，支持商户入驻审核、菜品管理、浏览购物车、下单、模拟支付、订单状态流转、轻量配送与平台运营管理，并在此基础上提供安全、可控、可审计的 AI 对话式辅助服务（下单、催单、评价）。

本期的范围由三条主线划定，未进入这三条主线的功能一律列入"本期不包含"：

1. **平台交易闭环**：顾客浏览下单支付、商户处理订单、骑手接单送达、顾客评价。
2. **AI 受控下单**（本课题的创新点）：AI 只生成待确认草稿，经后端重校验与顾客确认后才产生正式订单。
3. **多商户证据**：商户注册即提交入驻申请、平台审核通过后方可经营，以及"商户只见本店数据、顾客只见本人订单"的数据隔离。

### 2.2 用户角色

| 角色 | 主要职责 | 承载端 |
| --- | --- | --- |
| 顾客 | 浏览商户与菜品、加购、下单、支付、查询订单、取消订单、评价 | 顾客端（移动端单页应用） |
| 商户 | 注册并提交入驻申请、维护菜品与分类、处理订单、维护营业信息、查看营业统计 | 商户端（后台单页应用） |
| 骑手 | 查看待接单列表、接单、配送、确认送达、查看本人任务与今日完成单数 | 骑手端（移动端单页应用） |
| 平台运营 | 审核商户、查询商户/用户/订单、创建骑手账号、查看操作日志与平台统计 | 运营端（由 Django Admin 承载） |

### 2.3 系统范围与边界

**包含**：多商户平台的核心交易闭环（浏览、购物车、下单、模拟支付、订单状态流转、取消、评价）；商户注册与入驻申请、平台审核；菜品分类与菜品管理；轻量配送（骑手自行接单与送达确认）；顾客端内置的 AI 点餐助手（对话式下单、催单、评价）；多商户数据隔离与越权防范；关键操作（含 AI 工具调用）的审计日志；平台运营的查询与统计。

**不包含（本期不实现，保留为后续扩展方向）**：

| 项 | 不纳入本期的原因 |
| --- | --- |
| 菜品规格与 SKU | 菜品的可交易属性收敛为价格与可售数量；引入规格会给下单、计价与库存链路带来第二套口径 |
| 真实支付对接 | 演示环境采用模拟支付，无需第三方支付资质与回调处理 |
| 短信、邮件、APP 推送 | 对外发送需要第三方服务与资质；站内通知由站内信承载 |
| 优惠券与积分体系 | 需要营销规则引擎与账务口径 |
| 复杂配送调度（地图导航、路径规划、智能派单、实时定位、拼单） | 需要地图服务与调度算法，超出"轻量配送"的定位 |
| 骑手评分与收入结算 | 需要新增"评价配送"这一维度与结算口径，且与本期评估指标无关 |
| 拒单与退单 | 接单即视为承诺配送；引入拒绝路径会增加状态分支 |
| 收藏菜品/商户 | 与交易主线无关 |
| 站内通知阅读界面（面向商户、骑手、顾客） | 站内信会写入并可在运营后台查看；面向各端的通知中心需要新增界面 |
| 系统参数配置 | 参数外置的收益低于维护成本 |
| 营业时间与打烊拦截 | 需要时间规则与顾客端拦截联动 |
| 商户列表的销量与距离展示 | 距离依赖地图定位；销量需要新增统计口径 |
| 完整的出餐状态（取餐中、待取餐等中间态） | 中间态会使状态数量翻倍，对主线无贡献 |

> 注：退款功能已纳入系统功能规划（见 3.2 节 F-A-11，标注为"后期实现项"）：订单状态枚举已预留"退款中（70）""已退款（80）"两个取值，退款流程将随该功能实现时启用。

### 2.4 功能优先级说明

| 优先级 | 含义 |
| --- | --- |
| 核心 | 本期必须实现，纳入验收 |
| 重要 | 本期应实现，纳入验收 |
| 后续 | 列入后续实现计划，实现时补充验收场景（本期不纳入验收） |

## 三、功能需求

### 3.1 功能结构

系统分为**四个端**，其中顾客端由两个功能块构成：

```
顾客端
  ├─ 基础交易：登录、浏览、购物车、下单、支付、订单、取消、地址、评价
  └─ AI 点餐助手：会话、槽位收集、草稿生成、后端校验、确认下单、催单、辅助评价
商户端：注册与入驻申请、审核状态、分类管理、菜品管理、订单处理、营业信息、营业统计
骑手端：登录、待接单列表、接单、送达确认、本人任务、今日完成单数
运营端：登录、商户审核、商户/用户/订单查询、骑手账号维护、平台统计、操作日志
```

### 3.3 核心用例

> 用例图建议：顾客、商户、骑手、平台运营四类参与者分别连接各自用例；顾客端内包含"AI 点餐助手"子流程。

#### UC-01 顾客浏览与下单

- **参与者：** 顾客
- **前置条件：** 顾客已登录；存在已通过审核的商户与在售菜品。
- **主流程：**
  1. 顾客浏览商户列表，进入某商户；
  2. 浏览菜品并加入购物车；
  3. 进入结算，选择收货地址、填写备注；
  4. 提交订单，生成"待支付"订单；
  5. 选择模拟支付，订单变为"已支付"。
- **异常流：**
  - 3a. 未选择收货地址 → 提示选择地址，不允许提交；
  - 4a. 购物车为空 → 拒绝下单；
  - 4b. 菜品已下架或可售数量不足 → 拒绝下单并提示原因；
  - 5a. 支付失败 → 订单保持"待支付"，可重试。
- **后置条件：** 生成订单，订单金额含商品金额与平台固定配送费，订单状态按状态机流转。

#### UC-02 顾客取消订单

- **参与者：** 顾客
- **前置条件：** 顾客已登录；存在本人名下的、状态为"待支付"或"已支付且未被接单"的订单。
- **主流程：** 顾客在订单详情发起取消 → 校验状态是否允许取消 → 订单变为"已取消"，记录状态变更日志。
- **异常流：** 订单状态不允许取消（已进入配送或已完成）→ 拒绝并提示。
- **后置条件：** 订单状态更新，历史可追溯。

#### UC-03 商户注册与入驻申请

- **参与者：** 商户（未入驻）
- **前置条件：** 该店铺尚未入驻本平台。
- **主流程：** 商户在商户端注册，填写账号、密码、店铺名称、联系电话、店铺地址、店铺简介 → 提交 → 系统创建状态为"待审核"的商户记录 → 商户可登录并查看审核状态。
- **异常流：** 账号已被占用 → 拒绝注册并提示；必填项缺失 → 拒绝提交并提示。
- **后置条件：** 生成一条"待审核"的商户记录，等待平台运营审核。

#### UC-04 平台运营审核商户

- **参与者：** 平台运营
- **前置条件：** 存在待审核的商户入驻申请。
- **主流程：** 运营查看申请 → 通过或驳回 → 商户状态变更。
- **异常流：** 商户不存在 → 提示；提交的动作非法 → 拒绝并提示。
- **后置条件：** 商户状态变更为"已通过"或"已驳回"；审核通过后该商户方可使用菜品管理与订单处理功能。

#### UC-05 商户管理菜品

- **参与者：** 商户
- **前置条件：** 商户已注册、已通过审核并登录。
- **主流程：** 商户新增/编辑分类 → 新增/编辑菜品、设置价格与可售数量 → 上架。
- **异常流：** 商户尚未通过审核 → 拒绝进入菜品管理，仅可查看入驻状态。
- **后置条件：** 菜品数据仅作用于本商户（数据隔离）。

#### UC-06 顾客使用 AI 点餐助手辅助下单（核心用例）

- **用例编号：** UC-06
- **名称：** AI 点餐助手对话式辅助下单
- **参与者：** 顾客（主）、AI 点餐助手（系统）
- **目标：** 顾客在顾客端内通过自然语言对话，生成一张**待确认的订单草稿**。
- **前置条件：** 顾客已登录顾客端；存在已通过审核的商户与在售菜品。
- **触发条件：** 顾客在顾客端打开 AI 点餐助手并表达点餐意图。

**主流程：**

1. 顾客打开 AI 点餐助手，系统以当前登录顾客的身份创建会话；
2. AI 引导顾客提供下单信息：**商户、菜品、数量、地址**；
3. 顾客用自然语言表达需求；
4. AI 调用 `search_merchant` 定位商户；
5. AI 调用 `search_menu(merchant_id)` 定位菜品；
6. AI 汇总草稿内容，调用 `validate_draft` 由**后端重新校验**价格、库存、商户归属与地址合法性；
7. 校验通过后，AI 调用 `create_draft` 生成订单草稿，并向顾客展示草稿摘要（商户、菜品、数量、单价、总额、地址）；
8. 顾客确认无误 → 草稿转为正式订单（"待支付"）→ 进入模拟支付。

**异常流：**

- 4a. 无法确定商户 → AI 提示并请顾客澄清；
- 5a. 菜品不存在或已下架 → AI 给出候选请顾客选择；
- 6a. 可售数量不足、价格已变动或地址非法 → 后端拒绝，AI 向顾客说明原因并请其修改；
- 8a. 顾客未确认 → 草稿保持"待确认"状态，不生成订单。

**后置条件：** 生成一张待确认订单草稿；关键操作（工具调用、草稿创建、确认）写入审计日志。

#### UC-07 订单状态流转

- **参与者：** 系统（由各角色操作触发）
- **本期状态集合：** 待支付 → 已支付 → 待接单 → 配送中 → 已完成；可取消状态 → 已取消。
- **状态推进方式：** 顾客支付（待支付 → 已支付）；顾客取消（待支付或已支付 → 已取消）；商户接单（已支付 → 待接单）；骑手接单（待接单 → 配送中，同时记录骑手）；骑手确认送达（配送中 → 已完成）；商户取消（可取消状态 → 已取消）。
- **主流程：** 每次状态变更校验迁移合法性，非法迁移被拒绝，并记录状态变更日志。
- **后置条件：** 订单状态合法推进，历史可追溯。
- **说明：** 各端接口对状态的表示方式属系统设计范畴（见系统设计说明书）。

#### UC-08 骑手接单与送达（轻量）

- **参与者：** 骑手
- **前置条件：** 存在状态为"待接单"且尚未分配骑手的订单。
- **主流程：** 骑手查看待接单列表 → 点击"接单"（订单归属本人并变为"配送中"） → 配送完成后点击"送达"（订单变为"已完成"，记录送达时间）。
- **异常流：** 订单已被他人接单 → 提示接单失败并刷新列表；订单状态不允许接单 → 拒绝并提示。
- **后置条件：** 订单配送状态更新，记录骑手、送达时间与完成时间。

#### UC-09 AI 点餐助手催单

- **参与者：** 顾客、AI 点餐助手（系统）
- **前置条件：** 顾客已登录；存在该顾客的进行中订单。
- **主流程：**
  1. 顾客表达催单意图（如"我的单怎么还没到"）；
  2. AI 调用 `get_order_status` 查询订单当前状态与骑手信息；
  3. AI 调用 `urge_order` 生成催单记录，并向商户（以及已分配的骑手）写入站内信；
  4. AI 向顾客回复当前进度与已催单。
- **异常流：** 无进行中订单 → AI 如实告知；订单已完成 → 说明无需催单。
- **后置条件：** 生成催单记录与站内信；操作写入审计日志。

#### UC-10 AI 点餐助手辅助评价

- **参与者：** 顾客、AI 点餐助手（系统）
- **前置条件：** 顾客已登录；存在该顾客的已完成订单且尚未评价。
- **主流程：**
  1. 顾客表达评价意图；
  2. AI 定位可评价的订单，询问评分（1–5 星）与留言；
  3. AI 调用 `submit_review` 提交评价；
  4. AI 向顾客确认评价已提交。
- **异常流：** 订单未完成或已评价 → AI 如实告知。
- **后置条件：** 生成评价记录；操作写入审计日志。

### 3.4 全局业务规则

| 编号 | 规则 |
| --- | --- |
| R1 | 一个订单仅属于**一个**商户。 |
| R2 | 订单状态变更必须符合状态机定义；非法迁移一律拒绝，且每次实际变更写入状态变更日志。 |
| R3 | 未通过审核的商户不得使用菜品管理与订单处理功能；其登录后只能查看入驻审核状态。 |
| R4 | 各端的业务操作以本人作用域为限：商户仅限于本店数据，骑手仅限于本人任务，顾客仅限于本人订单、地址、草稿与会话。 |
| R5 | AI **不得**直接创建正式订单或发起支付。 |
| R6 | 草稿生成前**必须**经后端重校验。 |
| R7 | AI 工具调用与草稿的创建/确认**均**记录操作日志。 |
| R8 | AI 点餐助手**仅能**操作当前登录顾客本人的数据，不得跨顾客访问。 |

## 四、非功能需求

### 4.1 性能需求

- 常规页面与接口响应时间：在校园/单机演示环境下 ≤ 2 秒；
- 支持较小规模的并发访问（教学演示级别），重点保证功能正确性。

### 4.2 安全需求

- **身份认证：** 基于令牌的登录认证，四类角色（顾客、商户、骑手、平台运营）各自使用独立的令牌签发与校验；
- **权限控制（RBAC）：** 按角色授权；平台运营额外要求运营账号标识（`is_staff`）；商户须通过入驻审核后方可使用经营相关功能（见 R3）；
- **数据隔离与越权防范：** 商户只能访问/操作自己的菜品与订单；骑手只能处理分配给自己的任务；顾客只能访问本人订单、地址、草稿与会话；以 `merchant_id` / `rider_id` / `user_id` 做作用域校验；
- **AI 安全：** AI 无直接写库权限；AI 相关接口与普通业务接口**共用同一套认证与作用域校验**，不得存在免认证入口；草稿须经后端重校验并经顾客确认；对模型输入输出做必要校验；
- **审计：** 关键操作（含 AI 工具调用）记录操作者、动作、时间与前后状态，支持追溯。

### 4.3 可靠性

- 下单与支付等关键操作使用数据库事务，保证数据一致性；
- 订单状态迁移遵循状态机，防止脏状态；
- 数据库操作失败时保持订单与支付记录的一致性（不产生"已支付无订单"或"有订单无支付记录"的中间态）。

### 4.4 易用性

- 前端界面简洁清晰，流程符合直觉；
- 商户在待审核期间能清楚看到当前所处的审核环节；
- AI 对话对缺槽、歧义给出明确提示。

### 4.5 可维护性

- 按业务模块划分代码，接口清晰；
- 数据库配置可切换，关键配置外置，便于部署。

## 五、评估指标定义（AI 功能）

为量化评估 AI 辅助服务的效果与安全性，定义以下指标：

1. **槽位字段准确率（Field Accuracy）**
   - 定义：对测试用例集，AI 最终生成的草稿中"商户、菜品、数量、地址"四类字段与标准答案一致的比例。
   - 计算：`准确率 = 正确字段数 / 总字段数`；可按字段分别统计准确率。
   - 目的：衡量对话到结构化订单的映射质量。

2. **下单耗时（Ordering Time）**
   - 定义：从发起下单到生成订单（草稿确认）的平均耗时。
   - 对比：AI 辅助下单 vs 人工逐项下单。
   - 目的：衡量 AI 辅助是否提升效率。

3. **非法状态与越权测试通过率（Block Rate）**
   - 定义：在构造的非法请求（跨商户访问、跨顾客访问、非法状态迁移、AI 越权写库尝试等）中，被系统正确拦截的比例。
   - 计算：`通过率 = 正确拦截数 / 非法请求总数`。
   - 目的：衡量系统的安全性与鲁棒性。

## 七、约束与假设

- 支付为**模拟支付**，不接入真实支付渠道；
- **退款列为后期实现项**：订单状态枚举已预留"退款中（70）""已退款（80）"取值（实现前不可达）；退款功能（申请、审核、退款记录）随该功能实现时启用；
- **菜品不含规格与 SKU**：菜品的可交易属性为价格与可售数量，不存在规格选择与规格级独立定价；
- **库存口径**：菜品可售数量用于下单时的可售校验，本期**不实现下单后的自动扣减**，数量由商户在商户端维护；
- **配送费口径**：配送费为平台统一固定值 **2 元**，下单时作为订单金额的一部分记录在订单上（快照），本期不实现按商户、距离或订单金额的计费规则；
- **商户列表展示口径**：只展示商户名称、简介、评分（评价均值的真实计算结果）与配送费；不展示销量与距离；
- **骑手端口径**：只提供接单配送相关功能与今日完成单数；不提供评分与收入；
- **中间态口径**：不设"已接单未配送""取餐中"等中间态，骑手接单即进入配送中；
- 不实现真实短信/邮件/APP 推送，站内通知用站内信实现；演示环境下登录验证码可直接返回，便于测试；
- 配送为**轻量实现**，不含地图导航、路径规划、智能派单与实时定位；
- 假设商户数量与订单量为教学演示规模；
- 大语言模型存在不确定性，系统通过"草稿单 + 后端重校验 + 顾客确认"降低其影响。
