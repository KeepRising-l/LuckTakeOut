## 一、引言

### 1.1 编写目的

本文档用于明确"基于 Python 的外卖平台"的功能需求与非功能需求，作为系统设计、编码实现与测试验收的依据。预期读者为开发者、指导教师与评审人员。

### 1.2 项目背景

本系统是一个**多商户**外卖平台：平台作为运营方，接入并审核多个入驻商户；商户各自维护菜品与订单；骑手负责配送；消费者在平台内浏览、下单、支付与评价；平台另设"客服"角色，借助大语言模型为顾客提供**对话式辅助服务（下单、催单、评价）**。

### 1.3 术语与定义

| 术语 | 含义 |
| --- | --- |
| 商户（Merchant） | 入驻平台的餐饮商家 |
| 顾客（Customer） | 下单的终端消费者 |
| 骑手（Rider） | 负责订单配送的配送人员 |
| 客服（Customer Service） | 代表/协助顾客完成下单、催单、评价的操作人员 |
| 平台运营（Admin） | 平台的运营管理人员，负责商户审核与全局管理 |
| 草稿单（Order Draft） | AI 辅助生成的、尚未确认的待下单内容，不产生真实交易 |
| 槽位（Slot） | 下单所需的结构化字段：商户、菜品、规格、数量、地址 |
| 越权 | 用户访问了不属于自己权限范围的数据或功能 |

## 二、系统概述

### 2.1 系统目标

实现一个可运行的多商户外卖平台，支持商户入驻审核、菜品管理、浏览购物车、下单、模拟支付、订单状态流转、轻量配送与平台运营管理，并在此基础上提供安全、可控、可审计的 AI 对话式辅助服务（下单、催单、评价）。

### 2.2 用户角色

| 角色 | 主要职责 |
| --- | --- |
| 顾客 | 浏览商户与菜品、加购、下单、支付、查询订单、申请退款、评价 |
| 商户 | 入驻申请、维护菜品与规格、处理订单、查看营业信息 |
| 骑手 | 查看待接单列表、接单、配送、确认送达 |
| 客服 | 通过对话协助顾客完成下单、催单与评价 |
| 平台运营 | 审核商户、管理商户/用户/订单、查看操作日志 |

### 2.3 系统范围与边界

- **包含**：多商户平台的核心交易闭环、订单状态流转、退款（简化）、**配送（轻量：骑手接单与送达）**、**AI 辅助下单 / 催单 / 评价**、操作审计。
- **不包含（本期）**：真实支付对接（采用模拟支付）、真实短信/邮件/APP 推送、优惠券与积分体系、复杂配送调度（地图导航、路径规划、智能派单、实时定位、拼单）。

## 三、功能需求

### 3.1 功能结构

系统分为五个功能域：

- **用户端（顾客）**：登录、浏览、购物车、下单、支付、订单、退款、评价、地址。
- **商户端**：入驻、菜品与规格管理、订单处理、营业信息。
- **配送端（骑手，轻量）**：待接单列表、接单、确认送达。
- **平台运营端**：商户审核、全局管理、操作日志。
- **AI 客服端**：会话、槽位收集、草稿生成、后端校验、确认下单、催单、辅助评价。

### 3.3 核心用例

（用例图建议：顾客、商户、骑手、客服、平台运营五类参与者，分别连接各自用例；系统边界内包含"AI 辅助服务"子流程。）

#### UC-01 顾客浏览与下单

- **参与者：** 顾客
- **前置条件：** 顾客已登录；存在已通过审核且在营业的商户。
- **主流程：**
  1. 顾客浏览商户列表，进入某商户；
  2. 浏览菜品并按规格加入购物车；
  3. 进入结算，选择收货地址、填写备注；
  4. 提交订单，生成"待支付"订单；
  5. 选择模拟支付，订单变为"已支付"。
- **异常流：**
  - 3a. 未选择地址 → 提示选择地址；
  - 4a. 购物车为空 → 拒绝下单；
  - 5a. 支付失败 → 订单保持"待支付"，可重试。
- **后置条件：** 生成订单，订单状态按状态机流转。

#### UC-02 商户管理菜品

- **参与者：** 商户
- **前置条件：** 商户已通过审核并登录。
- **主流程：** 商户新增/编辑分类 → 新增/编辑菜品与规格、设置价格与库存 → 上架。
- **后置条件：** 菜品数据仅作用于本商户（数据隔离）。

#### UC-03 平台运营审核商户

- **参与者：** 平台运营
- **前置条件：** 存在待审核的商户入驻申请。
- **主流程：** 运营查看申请 → 通过或驳回 → 记录审核结果与操作日志。
- **后置条件：** 商户状态变更（待审核 → 通过/驳回）。

#### UC-04 AI 客服辅助下单（核心用例）

- **用例编号：** UC-04
- **名称：** 客服对话式辅助下单
- **参与者：** 客服（主）、AI 助手（系统）、顾客（授权方）
- **目标：** 在顾客授权后，通过自然语言对话生成一张**待确认的订单草稿**。
- **前置条件：** 客服已登录；顾客已授权本次代下单；商户与菜品数据存在。
- **触发条件：** 客服选择顾客并发起对话，顾客表达点餐意图。

**主流程：**

1. 客服选择目标顾客，创建会话；
2. AI 引导顾客提供下单信息：**商户、菜品、规格、数量、地址**；
3. 顾客用自然语言表达需求；
4. AI 调用 `search_merchant` 定位商户；
5. AI 调用 `search_menu(merchant_id)` 定位菜品；
6. AI 调用 `get_item_specs(product_id)` 获取规格与单价；
7. AI 汇总草稿内容，调用 `validate_draft` 由**后端重新校验**价格、库存、商户归属与地址合法性；
8. 校验通过后，AI 调用 `create_draft` 生成订单草稿，并向顾客展示草稿摘要（商户、菜品、规格、数量、单价、总额、地址）；
9. 顾客确认无误 → 草稿转为正式订单 → 进入模拟支付。

**异常流：**

- 4a. 无法确定商户 → AI 提示并请顾客澄清；
- 5a. 菜品不存在/已下架 → AI 给出候选请顾客选择；
- 7a. 库存不足、价格已变动或地址非法 → 后端拒绝，AI 向顾客说明原因并请其修改；
- 9a. 顾客未确认或超时 → 草稿作废，不生成订单。

**后置条件：** 生成一张待确认订单草稿；关键操作（工具调用、草稿创建、确认）写入审计日志。

**业务规则：**

- R1. AI **不得**直接创建正式订单或发起支付；
- R2. 草稿生成前**必须**经后端重校验；
- R3. 一个订单仅属于**一个**商户；
- R4. AI 工具调用与草稿的创建/确认**均**记录操作日志；
- R5. 客服操作需以顾客授权为前提。

#### UC-05 订单状态流转

- **参与者：** 系统（由各角色操作触发）
- **状态说明：** 待支付 → 已支付 → 待接单 → 配送中 → 已完成；退款中 → 已退款；可取消状态 → 已取消。
- **主流程：** 每次状态变更校验迁移合法性，非法迁移被拒绝，并记录状态变更日志。
- **后置条件：** 订单状态合法推进，历史可追溯。

#### UC-06 申请退款（简化）

- **参与者：** 顾客、商户/平台运营
- **主流程：** 顾客对已支付未完成订单发起退款申请 → 商户或运营确认 → 订单进入"退款中" → 模拟退款成功 → 订单"已退款"。
- **异常流：** 订单状态不允许退款 → 拒绝申请。

#### UC-07 骑手接单与送达（轻量）

- **参与者：** 骑手
- **前置条件：** 存在状态为"待接单"的订单。
- **主流程：** 骑手查看待接单列表 → 点击"接单"（订单变为"配送中"，记录骑手） → 配送完成后点击"送达"（订单变为"已完成"）。
- **异常流：** 订单已被他人接单 → 提示接单失败并刷新列表。
- **后置条件：** 订单配送状态更新，记录骑手与送达时间。

#### UC-08 AI 客服催单

- **参与者：** 客服、AI 助手、顾客
- **前置条件：** 顾客已授权；存在该顾客的进行中订单。
- **主流程：**
  1. 顾客表达催单意图（如"我的单怎么还没到"）；
  2. AI 调用 `get_order_status` 查询订单当前状态与骑手信息；
  3. AI 调用 `urge_order` 生成催单记录，并向商户/骑手发送站内通知；
  4. AI 向顾客回复当前进度与已催单。
- **异常流：** 无进行中订单 → AI 如实告知；订单已完成 → 说明无需催单。
- **后置条件：** 生成催单记录；操作写入审计日志。

#### UC-09 AI 客服辅助评价

- **参与者：** 客服、AI 助手、顾客
- **前置条件：** 顾客已授权；存在该顾客的已完成订单且尚未评价。
- **主流程：**
  1. 顾客表达评价意图；
  2. AI 定位可评价的订单，询问评分（1–5 星）与留言；
  3. AI 调用 `submit_review` 提交评价（菜品/商户）；
  4. AI 向顾客确认评价已提交。
- **异常流：** 订单未完成或已评价 → AI 如实告知。
- **后置条件：** 生成评价记录；操作写入审计日志。

## 四、非功能需求

### 4.1 性能需求

- 常规页面与接口响应时间：在校园/单机演示环境下 ≤ 2 秒；
- 支持较小规模的并发访问（教学演示级别），重点保证功能正确性。

### 4.2 安全需求

- **身份认证：** 基于会话/令牌的登录认证；
- **权限控制（RBAC）：** 顾客、商户、骑手、客服、平台运营五类角色，按角色授权；
- **数据隔离与越权防范：** 商户只能访问/操作自己的菜品与订单；骑手只能处理分配给自己的任务；作用域校验（merchant_id / rider_id）防止越权；消费者只能访问本人订单；
- **AI 安全：** AI 无直接写库权限；草稿须经后端重校验与顾客确认；对模型输入输出做必要校验；
- **审计：** 关键操作（含 AI 工具调用）记录操作者、动作、时间与前后状态，支持追溯。

### 4.3 可靠性

- 下单与支付等关键操作使用数据库事务，保证数据一致性；
- 订单状态迁移遵循状态机，防止脏状态。

### 4.4 易用性

- 前端界面简洁清晰，流程符合直觉；
- AI 对话对缺槽、歧义给出明确提示。

### 4.5 可维护性

- 按业务模块划分代码，接口清晰；
- 数据库配置可切换，关键配置外置，便于部署。

## 五、评估指标定义（AI 功能）

为量化评估 AI 辅助服务的效果与安全性，定义以下指标：

1. **槽位字段准确率（Field Accuracy）**
   - 定义：对测试用例集，AI 最终生成的草稿中"商户、菜品、规格、数量、地址"五类字段与标准答案一致的比例。
   - 计算：`准确率 = 正确字段数 / 总字段数`；可按字段分别统计准确率与召回率。
   - 目的：衡量对话到结构化订单的映射质量。

2. **下单耗时（Ordering Time）**
   - 定义：从发起下单到生成订单（草稿确认）的平均耗时。
   - 对比：AI 辅助下单 vs 人工逐项下单。
   - 目的：衡量 AI 辅助是否提升效率。

3. **非法状态与越权测试通过率（Block Rate）**
   - 定义：在构造的非法请求（跨商户访问、非法状态迁移、AI 越权写库尝试等）中，被系统正确拦截的比例。
   - 计算：`通过率 = 正确拦截数 / 非法请求总数`。
   - 目的：衡量系统的安全性与鲁棒性。

## 七、约束与假设

- 支付为**模拟支付**，不接入真实支付渠道；
- 不实现真实短信/邮件/APP 推送，站内通知用站内信实现；
- 配送为**轻量实现**，不含地图导航、路径规划与智能派单；
- 假设商户数量与订单量为教学演示规模；
- 大语言模型存在不确定性，系统通过"草稿单 + 后端校验 + 顾客确认"降低其影响。
