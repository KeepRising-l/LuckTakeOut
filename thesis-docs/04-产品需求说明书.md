# 产品需求说明书（PRD）

**项目名称：** 基于 Python 的外卖平台的管理与实现（LuckTakeOut）

**文档定位：** 本文档回答三个问题——**这个项目为什么这样做设计、解决了什么问题、研究背景与意义是什么**。它不重复功能清单：功能需求（做什么、验收标准）以 `02-需求分析.md` 为唯一权威源，本文档解释其背后的设计动机与取舍理由。

**版本：** 第 1 稿（2026-10-13）

---

## 一、项目概述

### 1.1 一句话定义

一个**多商户**外卖平台：平台作为运营方接入并审核商户，顾客跨商户浏览下单，商户处理订单，骑手抢单配送；在此基础上，顾客端内置一个**受控的 AI 点餐助手**——大语言模型只生成"待确认草稿单"，经后端重校验与顾客确认后才产生真实订单。

### 1.2 项目要解决什么问题

| # | 问题 | 具体表现 | 本项目的应对 |
| --- | --- | --- | --- |
| 1 | 多商户业务闭环的工程实现 | 商户入驻与审核、菜品管理、下单支付、订单流转、轻量配送、评价，涉及四个参与方与十余个业务模块 | 用单一可控的技术栈（Django + Vue 3）实现完整闭环，见第三章 |
| 2 | **模型输出不可信**（核心研究问题） | 大语言模型可能在价格、库存上产生"幻觉"，若让模型直接写库或发起扣款，业务数据不可信 | "草稿单 → 后端重校验 → 顾客确认"机制：模型永远碰不到正式订单的写入口 |
| 3 | **AI 权限边界与可审计性** | AI 若走"特权通道"，会绕过认证、越权、无迹可查 | AI 工具接口与人工接口共用同一套认证、作用域校验与业务规则；每次工具调用写入审计日志 |
| 4 | 多商户数据隔离 | 商户 A 能看到商户 B 的订单与菜品、顾客能看到他人的订单 | 以 `merchant_id` / `user_id` / `rider_id` 做服务端作用域过滤，越权请求返回 403 |
| 5 | 演示与教学场景的可复现性 | 大型平台的分布式架构无法在单机、答辩教室环境复现 | SQLite 零配置默认 + 可一键切 MySQL 8；前端构建产物由 Django 同源托管，单端口演示 |

### 1.3 与同类项目的差异

| 对比对象 | 差异点 |
| --- | --- |
| 开源"外卖/点餐"教学项目 | 多数为**单商户**（单个餐饮企业自营点餐），没有入驻审核、多租户隔离与平台运营语义；本项目补齐了"平台方"这一角色 |
| 大型平台的分布式实现 | 微服务、消息队列、调度算法对教学规模不必要；本项目用单体 + 模块化换取可读性与可复现性 |
| 一般"套壳 AI"应用 | 模型直接调接口写数据；本项目把 AI 限制在"生成草稿"这一无副作用环节，把安全边界留在服务端 |

## 二、研究背景与意义

### 2.1 研究背景

**（1）外卖平台是多商户系统的典型形态。** 以美团、饿了么为代表的平台，本质上都是"一个平台、多方参与"：平台运营方接入并审核大量商户，商户各自维护菜品与订单，骑手提供运力，消费者跨商户浏览下单。这种形态对系统的**数据隔离、权限控制、交易一致性**提出了明确要求，是软件工程教学中"复杂业务系统"的良好载体。

**（2）大语言模型的函数调用（Function Calling）能力已经成熟。** 从 ReAct（推理与行动交替）到工业界标准化的工具调用接口，模型已经能够以结构化参数调用后端接口。"用自然语言对话完成业务操作"在技术上可行，但在业务系统中落地仍存在信任问题：模型输出不确定，可能产生幻觉，且缺乏对模型操作的审计与越权防范。

**（3）教学中缺少"中间态"的实现参考。** 现有开源实现要么停留在单商户的增删改查（不涉及平台语义），要么直接对标大型平台的分布式复杂度（不适合单机演示与教学复现）。"多商户业务闭环 + 安全可控的 AI 交互"这一中间态，缺少一个完整、可运行、文档齐全的参考实现。

### 2.2 研究意义

**理论意义：** 本课题探索大语言模型在受控业务系统中的落地范式——模型只承担"意图理解与槽位抽取、生成待确认草稿"的职责，真实的数据写入与交易操作始终由后端按业务规则重新校验后执行。该"草稿-校验-确认"范式对"如何在业务系统中安全地引入 AI 能力"具有参考价值；同时课题给出了可量化的评估方法（槽位字段准确率、下单耗时对比、非法请求拦截率），使 AI 功能的实用性与安全性可以被度量而非空口断言。

**实践意义：** 完成一套可运行的多商户外卖平台（含四个端、入驻审核链路、订单流转与 AI 点餐助手），成果可直接用于教学演示；其需求文档、规格体系、测试与部署材料构成一份完整的工程实践样本。

## 三、产品定位与设计目标

### 3.1 产品定位

- **面向对象：** 教学演示与中小型场景的参考实现，单机可运行；
- **产品边界：** 覆盖"交易闭环 + 多商户治理 + 受控 AI 辅助"三条主线，不追求大平台的功能广度（明确的不做清单见 3.3）；
- **品质标准：** 面向**答辩与真实演示**——界面上不允许存在假数据（假销量、假评分、假距离一律清除或改为真实计算），所有展示值必须来自真实数据链路。

### 3.2 设计目标

1. 一个可运行的完整闭环：顾客浏览下单支付 → 商户接单处理 → 骑手接单配送 → 顾客评价；
2. 多商户语义齐全：注册即提交入驻申请、平台审核、未过审不能经营、商户间数据互相隔离；
3. AI 点餐助手安全可控：只生成草稿、后端重校验、顾客确认后转正式订单、全程审计；
4. 工程化可交付：需求 → 规格 → 实现 → 测试全链路对齐（47 条可验收要求、36 项自动化测试），新电脑可快速复现。

### 3.3 三条主线与"本期不包含"

范围收敛的标准是三问：**砍掉后三条主线是否仍自洽？是否引入新口径需要额外解释？是否引入新的数据依赖？** 三条主线为：

1. **平台交易闭环**——顾客→商户→骑手→评价的完整链路；
2. **AI 受控下单**（本课题创新点）——草稿单机制与审计；
3. **多商户证据**——入驻审核 + 数据隔离，证明"多商户"并非名义上的。

未进入三条主线的功能（菜品规格与 SKU、真实支付、推送、优惠券积分、复杂配送调度、骑手结算、营业时间拦截等）全部移入"本期不包含"清单，每项附不纳入原因，完整清单见 `02-需求分析.md` 第 2.3 节。**该清单是设计的一部分**：答辩中"为什么不做什么"与"做了什么"同样重要。其中退款功能已由"本期不包含"调整为**后续实现项**（2026-10-14）：需求稿已收录（F-A-11），订单状态枚举已预留"退款中/已退款"取值。

### 3.4 角色与端

四类角色：**顾客 / 商户 / 骑手 / 平台运营**。AI 点餐助手是顾客端内的一个功能，不构成独立角色、不单独成端——它代表当前登录顾客发起操作，作用域归属该顾客（此口径经 2026-10-11 修订确认）。

## 四、关键设计决策及理由（核心章节）

> 本章是本文档的重点：每个决策给出"选择、理由、代价"三段式，供评审与答辩问答使用。

### 4.1 为什么是"多商户"而不是单商户

- **选择：** 平台接入多个商户，商户注册即提交入驻申请，运营审核通过后方可经营。
- **理由：** "多商户"是外卖平台区别于普通点餐系统的本质特征，它带出三块有分量的工程内容——入驻审核（平台治理）、数据隔离（安全）、平台运营（查询与统计）。单商户系统无法体现这些，业务深度不足。
- **代价：** 所有商户端接口必须带作用域过滤与审核门槛（本项目以 `merchant_approved_required` 装饰器统一实现，22 处经营接口统一挂载），复杂度高于单商户，但这正是设计目标所在。

### 4.2 为什么后端选 Django，而不是 FastAPI 等

- **选择：** Django（含 ORM、迁移、认证、Admin）。
- **理由（四条）：**
  1. **Admin 开箱即用**：平台运营端（商户审核、全局查询、骑手账号维护、操作日志）直接由 Django Admin 承载，无需为运营端单独开发前后端。FastAPI 需要自行开发或用第三方组件补齐这一块，而运营端恰是多商户平台不可缺少的一环；
  2. **ORM 与迁移一体化**：十余个业务模块、19 张业务表由同一套迁移体系管理（18 个项目迁移），FastAPI 需要自行组合 ORM 与迁移工具；
  3. **认证与角色体系可复用**：四类角色均建立在 `django.contrib.auth` 之上（顾客/商户/骑手档案一对一关联账号，运营用 `is_staff` 表达）；
  4. **性能不是本课题瓶颈**：单机教学规模下，FastAPI 的异步高并发与自动接口文档优势与本课题痛点不重合；接口契约由需求与规格文档统一约定，不依赖自动生成。
- **代价：** 视图层手写函数视图 + 统一响应封装（`{code, info, data}`），放弃了 Django REST Framework 的序列化器与视图集抽象——因为本项目不设服务层，直接用 ORM 更直白，减少教学规模的抽象层数（见 `03-系统设计.md` 1.2 的分层取舍）。

### 4.3 为什么前端做"三端独立 SPA + 单仓库"

- **选择：** npm workspaces monorepo：`apps/customer`（Vant 4，移动端 H5）、`apps/merchant`（Element Plus + ECharts，桌面后台）、`apps/rider`（Vant 4，移动端）三个独立应用 + `packages/shared` 共享包。
- **理由：**
  1. "端"的交互形态差异大（移动端底部导航 vs 桌面后台侧边栏），共用一套页面代码会互相牵制；独立应用各自构建、互不影响；
  2. 但**后端契约是同一套**（同一批 JSON 接口、同一套 ResultAPI 格式、同一套订单状态取值），因此把请求封装（axios 拦截器、401 处理）、token 存储、格式化、**订单状态文案表**下沉到共享包——三端对同一状态的取值绝不会漂移；
  3. 构建产物（各应用 `dist`）由 Django **同源托管**（`/`、`/merchant/`、`/rider/`）：单端口演示、无跨域配置、答辩换机不用装 nginx。
- **代价：** 需要维护 workspaces 工程结构；对多应用构建脚本的健壮性有要求（本项目 `npm run build` 三端一次构建）。

### 4.4 为什么最小 MVP 收敛（砍掉"可选"档）

- **选择：** 需求按最小可行范围收敛为第 3 稿（2026-10-11），第 4 稿（2026-10-14）在此基础上订正商户订单口径并将退款纳入后续规划；优先级只保留"核心/重要"两档，未纳入项进"本期不包含"清单。
- **理由：** 功能堆叠会引入多套口径（例如退款状态、SKU 定价、"取餐中"中间态），使状态机、计价与库存链路翻倍复杂，而三条主线并不会因此更完整；答辩与论文评价的是**做深**而非**做多**。收敛也直接产生了"设计决策"这一论文素材（为什么不做，是有论证的）。
- **代价：** 功能覆盖面收窄。应对方式：每项"不做"都附原因，并作为"后续扩展方向"保留（论文的展望章节有东西可写）。

### 4.5 为什么 AI 只生成"草稿"（受控下单机制）

- **选择：** AI 通过 7 个工具（search_merchant / search_menu / validate_draft / create_draft / get_order_status / urge_order / submit_review）与业务交互；`create_draft` **只生成待确认草稿**，正式订单必须由顾客在前端确认后由服务端创建。
- **理由：**
  1. 模型输出不可信：价格、库存、商户归属一律以**数据库现状**为准，由后端在 `validate_draft` 中重新计算，模型组织错了参数也进不了正式订单；
  2. 权限边界统一：AI 接口与顾客端人工接口共用同一套 token 认证与作用域（会话、消息、草稿均归属登录顾客），不存在"免认证的 AI 入口"——历史上这一漏洞曾被真实修复（AI 四个接口补齐认证，见第五章"已消灭的问题"）；
  3. 可审计：工具调用、草稿创建/确认全部写 `operation_log`（`actor_role='ai'`），可追溯"AI 在什么时间以什么参数做了什么"。
- **代价：** 多一次确认交互，下单链路比"AI 直接下单"长一步——这一步正是安全性的载体，在评估中以"下单耗时"指标量化。

### 4.6 为什么设计订单状态机（而不是散在视图里改状态）

- **选择：** 状态取值 10-60（待支付/已支付/待接单/配送中/已完成/已取消），全部状态变更经 `order/state.py` 的 `change_status()`：查合法迁移表 → 落库 → 写 `order_status_log`；非法迁移被拒绝且不写日志。
- **理由：**
  1. 订单状态是全系统最关键的共享状态（顾客、商户、骑手、运营四个视角叠加），散落各处在所难免地会出现"配送中改回待接单"这类脏迁移；
  2. 单一入口让"什么状态下谁能做什么"变成一张**可检视的真值表**，测试可直接对着它构造合法/非法用例（36 项测试中有专门的迁移合法性用例）；
  3. 状态变更日志为"订单历史"与纠纷追溯提供数据。
- **代价：** 新增状态与流转都要维护迁移表；本项目通过"砍中间态"（骑手接单即配送中，不设"取餐中"）保持状态图简洁可控。

### 4.7 关键业务口径及其理由

| 口径 | 决策 | 理由 |
| --- | --- | --- |
| 配送费 | 平台统一固定值 **2 元**，下单时快照入订单（`delivery_fee` 字段） | 计费规则（距离/时段/动态定价）不属于三条主线；固定值保证"订单金额由服务端重算"的口径可验收。此前由客户端传值且不落库的做法被修正 |
| 库存 | 可售数量仅用于下单校验，**不自动扣减** | 自动扣减会引入"下单占库存-支付超时释放"的并发链路，超出教学规模；数量由商户在商户端自行维护 |
| 菜品规格 | **不含 SKU**，可交易属性仅价格与可售数量 | 规格会带来"下单、计价、库存"的第二套口径（见 4.4 的三问标准）。数据库层同步删除了 `product_spec` / `product_sku` 遗留表 |
| 订单状态表示 | 后端整数枚举是**唯一真值**，接口直接返回整数；文案由前端按视角映射（集中在 `packages/shared/orderStatus.ts`） | 此前顾客端与商户端各有一套映射、还出现过字符串映射，口径漂移。统一后"同一状态在顾客端显示'待接单'、在商户端显示'已接单，待骑手取餐'"这类视角差异由呈现层承担，数据层不再分裂 |
| 支付 | 模拟支付（不接真实渠道） | 真实支付需要第三方资质与回调处理，与"交易闭环"的验收目标无关 |
| 假数据 | 界面上不允许出现假销量、假评分、假距离 | **演示真实性**是答辩的底线：任何被评委看出的假值都会动摇整个项目的可信度。商户评分改为评价均值的真实计算（无评价显示"暂无评分"），销量与距离直接不再展示 |

### 4.8 为什么认证要"四类角色、独立盐值"

- **选择：** 基于 `django.core.signing` 自签名 token，顾客/商户/骑手/平台运营**各用独立盐值**；请求头 `Authorization: Bearer <token>`，有效期 7 天。
- **理由：**
  1. 零额外依赖（不引入 JWT 库），签名、过期校验由 Django 完成，教学场景可读性好；
  2. **角色隔离**：商户端的 token 换到顾客端接口上验签直接失败——独立盐值使四类凭证互不通用，比"同一 token + 角色字段判断"多一层结构性防护；
  3. 平台运营端额外要求 `is_staff`，运营权限与普通账号物理隔离。
- **代价：** 无法像 JWT 那样携带富声明（本项目不需要）、服务端无法主动吊销单个 token（教学规模可接受）。**密钥管理（2026-10-13 加固）：** `SECRET_KEY` 支持环境变量注入（`DJANGO_SECRET_KEY`，生产模式未注入则拒绝启动），开发/演示模式保留内置值以维持零配置；token 盐值（salt）并非机密，凭证安全性依赖 `SECRET_KEY`。

## 五、项目对"真实问题"的修复记录（设计决策的实证）

以下问题均在本项目演进中被**真实发现并修复**，是"设计不是拍脑袋"的证据，也是答辩时的加分素材：

1. **AI 接口曾完全无认证**：早期 AI 四个接口没有认证，前端甚至为此维护了一个"不附带令牌"的专门请求实例。修复后 AI 接口与顾客端共用认证，作用域取自登录态（不读请求体中的顾客标识——那是不可信的输入）。
2. **订单可被越权访问**：订单详情与模拟支付曾未校验归属。修复后按 `user` 归属过滤，他人订单一律不可见、不可支付。
3. **状态迁移无约束**：曾存在"配送中改回待接单""取消配送中订单"等脏操作。修复后全部经状态机，非法迁移被拒绝。
4. **骑手可冒名操作**：9 个配送接口曾无鉴权，任何人可冒充任意骑手抢单。修复后跨骑手越权返回 403。
5. **配送费口径漂移**：曾由客户端传值且不落库。修复为平台固定值、服务端重算、快照入库。
6. **展示假值**：商户评分曾写死 4.9、存在假销量与假距离。修复为真实计算或移除。
7. **下单无地址校验**：曾可不选地址提交订单。修复为下单前校验地址归属与合法性。
8. **密钥与运行配置硬编码**：`SECRET_KEY`、`DEBUG`、`ALLOWED_HOSTS` 曾写死在代码中。修复为环境变量注入（`DJANGO_SECRET_KEY` / `DJANGO_DEBUG` / `DJANGO_ALLOWED_HOSTS`），生产模式未注入密钥时拒绝启动。
