## 一、立题依据（课题研究的目的与意义及国内外研究现状）

### （一）课题研究的目的与意义

外卖平台包含顾客、商户、骑手与平台运营等多类参与方。平台既要支持商户入驻审核、菜品维护、订单处理和配送协同，也要确保不同商户、顾客及骑手只能访问各自权限范围内的数据。由此，系统设计不仅是页面与增删改查功能的组合，还涉及角色权限、数据作用域、订单状态和金额计算等相互关联的业务规则。

大语言模型可以把自然语言请求转化为结构化参数，但模型生成的菜品、价格、库存或地址信息不能直接视为业务事实。若由模型直接写入正式订单或触发支付，可能产生错误订单或越权操作。本课题拟研究的问题是：在保留对话式交互便利性的同时，如何将模型限制在可审查的业务边界内，并由后端承担校验与写入责任。

课题目标是使用 Python 技术栈设计并实现一个教学演示规模的多商户外卖平台，覆盖商户入驻与审核、菜品管理、顾客浏览和下单、模拟支付、订单状态流转、轻量配送、平台运营管理及评价等主流程；同时在顾客端实现受控 AI 点餐助手。AI 仅帮助理解意图、整理参数并生成待确认草稿，正式订单由服务端在顾客确认后创建，模型不直接写库或发起支付。

本课题的工程意义在于把多角色交易流程、数据隔离和审计要求落实到一个可运行的系统设计中；研究意义在于形成并验证"生成草稿—服务端校验—顾客确认—操作留痕"的应用方案，并通过槽位字段准确率、下单耗时及非法请求拦截率等指标评价其效果。上述指标是拟开展的测试内容，实际结果需在开发和测试后据实报告。

### （二）国内外研究现状

**1. 国内研究现状**

与外卖平台相关的国内研究包括平台经营机制建模和餐饮点餐系统设计两类。侯泽敏等从消费者配送时间敏感度出发讨论外卖平台盈利模式，为理解平台与消费者、商户及配送服务之间的协调关系提供了经济学视角[1]。校园点餐及外卖系统研究则围绕微信小程序、校园订餐和校园外卖场景开展系统设计与实现[2-4]。这些案例可为角色划分、点餐流程和系统开发步骤提供参照；其具体架构和业务边界与本课题不完全相同，不能直接等同于多商户平台治理。

大语言模型方向的国内研究涉及智能体、代码生成及可信问答等主题[5-6]。这类研究提示，模型生成能力与业务系统可靠性需要分别考察：模型的参数组织能力并不替代服务端对权限、数据与业务规则的校验。对本课题而言，这一认识支持将 AI 能力作为受控的交互入口，而非赋予模型独立的业务权限。

**2. 国外研究现状**

在线外卖平台研究关注平台服务创新、参与方互动及配送服务等问题[7-8]。校园订餐系统的工程论文展示了移动应用、实时点餐以及不同平台技术路线的实现案例[9-11]。这些研究从业务参与方和特定使用场景提供了分析素材，但其研究目标、系统规模和技术条件各不相同，需结合本项目的教学演示边界进行取舍。

大语言模型工具调用研究则重点讨论模型如何识别工具、生成参数并完成多步任务。ToolLLM/ToolBench、Gorilla 等工作探索了面向真实 API 的工具调用能力与评测方法[12-13]；相关智能体综述归纳了研究框架、应用和挑战[14-15]；ReAct 提出将推理与行动交替的提示范式[16]。这些成果为对话式工具调用提供了方法背景，但其能力评测不能替代面向具体交易系统的身份认证、数据作用域校验、二次确认与审计设计。

**3. 研究述评与本课题切入点**

已有研究分别讨论平台经营机制、点餐系统案例和大语言模型智能体/工具调用[1-4,7-16]。对于本课题，值得进一步完成的是将多商户业务闭环与受控 AI 交互放在同一个可复现的教学系统中，明确模型做什么、服务端必须重新判断什么，以及哪些操作必须由顾客确认。本文不声称相关领域缺少研究或本系统具有普遍首创性；拟将工作定位为面向教学演示的工程设计与验证。

## 二、课题研究内容

### 1. 系统分析与范围界定

围绕顾客、商户、骑手和平台运营四类角色开展需求分析，明确主要用例、数据范围、异常路径和验收条件。顾客端覆盖登录、商户与菜品浏览、购物车、地址、下单、模拟支付、订单查询、允许范围内取消、退款（后期实现项）和评价；商户端覆盖注册并提交入驻资料、审核状态查询、菜品分类与菜品维护、订单处理和营业统计；骑手端覆盖待接单查询、接单、送达确认及本人任务查询；运营端由 Django Admin 承载商户审核、全局查询、骑手账号维护、统计和操作日志。

本期采用最小可行范围：不接真实支付，不实现菜品规格/SKU、复杂配送调度、实时定位、优惠券积分及真实短信/推送。购物车拟由顾客端本地维护；配送费按平台固定值 2 元计算并由服务端写入订单快照。退款列为后续实现项，本期不将其描述为已实现功能。

### 2. 总体架构与数据设计

系统采用前后端分离的模块化单体架构。后端使用 Django 提供 JSON 接口并统一响应格式；前端使用 Vue 3、Vite 与 TypeScript 构建顾客、商户、骑手三个独立单页应用；平台运营功能由 Django Admin 承载。数据库默认采用 SQLite，并保留通过环境变量切换至 MySQL 8 的方案。

数据设计围绕用户、商户、菜品、订单、支付、配送、评价、审计和 AI 会话/草稿等业务域展开。订单只归属一个商户，订单明细保存商品名称及单价快照，金额使用定点数类型。订单状态以服务端整数枚举作为唯一真值，所有状态变更经统一入口校验合法迁移并记录状态日志。商户、顾客和骑手接口必须在服务端按 merchant_id、user_id 或 rider_id 限定数据作用域。

### 3. 受控 AI 点餐与关键业务规则

AI 点餐助手作为顾客端功能，不构成独立角色。请求必须来自已登录顾客；工具接口与普通业务接口共用认证、权限和作用域检查。模型可调用的工具包括商户/菜品搜索、草稿校验与生成、本人订单状态查询、催单和辅助评价，但不得直接创建正式订单、修改库存或发起支付。工具调用、草稿创建和确认均计划写入操作审计日志。

拟将草稿生成和最终确认设计为两个校验节点。生成草稿时，后端依据数据库核验商户归属、菜品上下架状态、价格、可售数量及地址归属；顾客点击确认、草稿转为正式订单前，服务端再次读取当前数据并重验价格、可售数量、商户与地址。若价格、库存或其他关键内容发生变化，则拒绝按旧摘要直接下单，返回变化后的信息并要求顾客再次确认；订单地址以经检验后的快照保存。

现有设计材料说明本期库存用于可售校验，但不自动扣减或预留。因此，确认时重验只能降低草稿过期风险，不能在并发下提供库存预占保证；该限制写入系统说明，并通过教学演示规模下的测试如实描述。支付采用模拟商户接口。商户负责接单及允许状态下的取消，订单的完成由骑手送达确认触发。

### 4. 研究方法、技术路线与测试评估

研究与实现拟结合文献归纳、需求建模、模块化系统设计及软件测试。首先梳理外卖平台与大语言模型工具调用相关文献，并以需求规格形成角色、流程和边界；随后完成总体架构、数据库和状态机设计，再按业务模块实现前后端；最后通过单元、接口、集成和端到端测试检查主要流程与权限边界。技术路线为"文献与需求分析—架构及数据设计—核心业务实现—AI 受控流程实现—测试与指标评估—论文整理与答辩准备"。

测试计划覆盖入驻审核、商品维护、下单与模拟支付、订单状态迁移、骑手接单及送达、评价、AI 草稿确认和审计等主链路；构造跨商户、跨顾客、跨骑手访问及非法状态迁移用例，统计正确拦截比例。AI 功能拟使用预先定义的对话用例集，按商户、菜品、数量、地址四类槽位统计准确率；在相同测试条件下记录 AI 辅助与人工逐项下单耗时。测试构造方法、样本数量、运行环境和实测数据均需在实施后据实报告，不在开题阶段预设结果。

## 三、课题研究条件（材料、主要实验仪器设备等）

### 1. 软硬件条件

硬件条件按任务书要求准备：Windows 11 专业版，四核 2.0GHz 以上处理器、8GB 以上内存及 20GB 以上可用磁盘空间。开发软件计划采用 Python 3.12、Django 6.1，前端采用 Vue 3、Vite、TypeScript 与 Node.js 22，使用 Visual Studio Code 或 PyCharm、Git、Postman/curl 及 Django Test 等工具。Django 官方发布说明列明 6.1 支持 Python 3.12；Node.js 官方发布页将 22.x 列为 LTS。数据库默认 SQLite，可选 MySQL 8。

### 2. 数据与外部依赖

系统以自建演示数据进行功能验证，不依赖真实顾客、商户或支付数据。模型服务采用 OpenAI 兼容接口作为可选依赖；未配置凭据时按材料设计使用内置规则化兜底方案，保证基础演示链路可运行。真实支付、短信和外部推送不纳入本期范围。

### 3. 可行性及风险控制

Django 提供 ORM、迁移与管理后台，适合本课题的模块化业务和平台运营界面；SQLite 可降低演示环境配置成本；前后端分离便于分别组织三类用户界面。若外部模型接口不可用，可切换到规则化兜底并单独标注测试模式；若时间紧张，优先保证交易闭环、数据隔离、订单状态规则及草稿确认安全边界，退款和真实第三方服务不纳入本期验收。当前提供的需求分析、系统设计和 PRD 是规划资料，不能单独证明代码功能已实现或测试已通过；最终论文应以实际代码、运行记录和测试结果为依据。
