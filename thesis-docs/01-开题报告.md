## 一、立题依据（课题研究的目的与意义及国内外研究现状）

### （一）课题研究的目的与意义

随着移动互联网与即时配送行业的快速发展，网络订餐外卖已成为餐饮消费的重要形态。以美团、饿了么为代表的大型外卖平台，本质上都是**多商户（多租户）平台**：平台作为运营方，接入并审核大量入驻商户；商户各自维护菜品与订单；骑手提供配送运力；消费者在平台内跨商户浏览、下单与评价。这种"一个平台、多方参与"的业务形态，对系统的**数据隔离、权限控制与交易一致性**提出了明确要求，是软件工程教学中"完整复杂业务系统"的良好载体。

与此同时，大语言模型（Large Language Model, LLM）与**函数调用（Function Calling）**技术日趋成熟，"用自然语言对话完成业务操作"在技术上已经可行。但将 LLM 引入真实业务系统面临一个根本矛盾：模型输出具有不确定性，可能在价格、库存等关键信息上产生"幻觉"，若允许模型直接写库或发起交易，业务数据将不可信、不可控、不可审计。**如何让 AI 在业务系统中"可用而不失控"，是一个兼具工程价值与研究价值的问题。**

本课题的研究目的有二：其一，使用 Python 技术栈设计并实现一个**多商户外卖平台**，覆盖商户入驻审核、菜品管理、浏览购物车、下单与模拟支付、订单状态流转、轻量配送与平台运营管理的完整业务闭环，并在服务端落实多商户数据隔离与越权防范；其二，在顾客端内置一个**受控的 AI 点餐助手**——大语言模型只承担"意图理解与参数组织、生成待确认订单草稿"的职责，价格、库存、商户归属由后端以数据库现状重新校验，正式订单必须经顾客确认后才由服务端创建，且 AI 的每次工具调用均写入操作审计。

研究意义体现在两个层面。**理论意义：** 本课题探索大语言模型在受控业务系统中的落地范式——"草稿生成 → 后端重校验 → 用户确认 → 全程审计"，该范式对"如何在业务系统中安全地引入 AI 能力"具有参考价值；课题同时给出可量化的评估方法（槽位字段准确率、下单耗时对比、非法请求拦截率），使 AI 功能的实用性与安全性能够被度量。**实践意义：** 课题成果是一套可运行、可复现（单机零配置即可部署演示）的完整系统，可直接用于教学演示，也可为中小型多商户平台的快速搭建提供参考实现与工程化样本。

### （二）国内外研究现状

**1. 国内研究现状**

（1）外卖平台与商业模式研究。国内学者对网络外卖平台的市场机制已有较系统的研究。侯泽敏等从双边市场理论出发，在竞争模型中引入消费者配送时间敏感度，研究外卖平台的盈利模式选择机制，揭示了平台匹配能力、市场竞争强度与抽成比例对最优收费策略的影响[1]。这类研究刻画了外卖平台"多方参与、平台居中协调"的商业本质，为平台型系统的功能设计（商户管理、订单流转、平台运营）提供了业务依据。随着行业成熟，行业分析普遍认为外卖平台已从"规模扩张"进入"精细运营"阶段，对平台的商户治理能力（入驻审核、数据隔离、运营审计）提出了更高要求。

（2）点餐/外卖系统的设计与实现。面向餐饮场景的信息系统在国内有大量工程实践。黄笑倩等面向高校场景设计并分析了校园"掌上食堂"APP，从需求调研、模块设计到可行性分析给出了完整过程[2]；张乐采用 Java 与 MySQL 基于微信平台开发了高校食堂自助点餐系统，支持校内用户自助点餐与食堂商家入驻[3]；王馗等基于微信小程序实现了包含用户端、移动端与商家管理端的点餐系统[4]。学位论文层面对校园外卖系统有更完整的研究，如山东大学李章恒的硕士论文围绕校园外卖场景完成了从推荐算法到系统实现与测试的完整工作[5]。总体来看，国内此类系统实现数量众多，但**多数面向单商户场景（单店点餐或单校食堂），平台化程度有限**：缺少平台方视角的商户入驻审核、多租户数据隔离与平台运营体系，"多商户"往往停留在概念层面。

（3）大语言模型智能体与工具调用。国内学术界对大语言模型智能体方向保持高度关注。董益宏等对基于大语言模型的代码生成智能体进行了系统性综述，指出智能体具备自主性、任务范围广泛性与工程实践性三大特征，工具集成与系统可靠性是工程落地的核心挑战[6]；王骞玥等研究了基于大语言模型的可信问答技术，强调在垂直业务场景中需对模型输出加以约束与校验[7]。这些工作表明，国内研究已充分认识到"模型能力"与"工程可靠性"的分离关系，但面向**真实交易类业务系统**的 LLM 安全集成（受控写操作、权限边界、操作审计）仍缺乏系统化的工程样本。

**2. 国外研究现状**

（1）外卖平台机制研究。国外学者较早从平台经济视角研究在线外卖（Online Food Delivery, OFD）市场。Sun 等研究了外卖平台的"三边"结构（消费者、餐厅、零工骑手），发现三边市场的竞争与服务策略不同于传统双边市场，平台的定价与服务策略需针对三边网络效应灵活调整[8]；Jiao 等基于中国饿了么平台数据的实证研究，验证了餐厅、配送系统与平台自身的服务绩效之间存在动态影响关系[9]。这类研究为平台系统的业务流程建模（多角色、多状态、多参与者协同）提供了理论参照。

（2）校园订餐系统的工程实践。国外在校园场景下的订餐系统研究侧重于移动化与特定技术方案的验证。Hamid 等采用改进瀑布模型为马来西亚高校开发了校园外卖移动应用 e-Runner，通过功能测试与可用性测试验证了系统的实用性[10]；Viraktamath 等提出基于内网的实时点餐系统，解决食堂排队拥堵问题[11]；Zhang 等尝试将区块链智能合约引入外卖平台，探索去中介化、免佣金的点对点外卖模式，并引入深度学习推荐模型[12]。这些工作展示了订餐系统在不同技术路线下的实现方式，但系统整体面向**单一组织或单一学校**，未涉及多商户平台的治理问题。

（3）大语言模型智能体与工具调用。这是与本课题 AI 部分最直接相关的研究方向。Qin 等提出 ToolLLM 框架与 ToolBench 数据集，让开源大模型掌握 16000+ 真实世界 API 的调用能力，并给出自动评测器 ToolEval[13]；Patil 等提出 Gorilla，使模型能够针对大规模 API 库生成正确的调用请求[14]；Wang 等与 Xi 等分别从智能体构建框架与"大脑-感知-行动"通用框架的角度对大语言模型智能体研究进行了系统综述[15][16]。上述研究极大提升了模型的工具调用**能力**，但其关注重心是"选对工具、调对参数"的能力评测，**对于"模型在高权限业务系统中的执行边界"——即如何设计系统使模型的操作被约束、可校验、可追溯——研究相对不足**。

**3. 现有研究的不足与本课题的切入点**

综上：多商户外卖平台在商业研究上成果丰富，但工程实现多停留于单商户或教学简化形态，缺少覆盖"入驻审核—数据隔离—平台运营—完整交易闭环"的完整样本；大语言模型工具调用研究集中于能力提升，缺少"模型输出不可信时如何设计业务安全边界"的系统化处理。本课题的切入点正在于此：以 Python 技术栈实现一个**多商户治理完备**的外卖平台，并设计**"草稿单 + 后端重校验 + 顾客确认 + 全程审计"的受控 AI 下单机制**，让大模型在业务系统中"可用而不失控"，并通过字段准确率、下单耗时与非法请求拦截率三个指标对 AI 功能进行量化评估。

## 二、课题研究内容

### 1. 系统分析

基于外卖平台的多角色业务特征，完成需求获取与建模：

（1）**角色与用例分析。** 系统共四类角色：顾客、商户、骑手、平台运营；AI 点餐助手定位为顾客端内的一个功能模块，代表当前登录顾客发起操作，不构成独立角色。围绕三条业务主线——平台交易闭环（浏览→下单→支付→接单→配送→评价）、AI 受控下单（草稿生成→校验→确认）、多商户治理（入驻审核+数据隔离）——梳理核心用例：顾客浏览与下单、顾客取消订单、商户注册与入驻申请、平台审核商户、商户管理菜品、顾客使用 AI 助手辅助下单、订单状态流转、骑手接单与送达、AI 助手催单与辅助评价等。

（2）**功能需求分析。** 按四端梳理功能需求并确定优先级（核心/重要两档）：顾客端（登录、浏览、购物车、下单、支付、订单、取消、地址、评价及 AI 助手）、商户端（注册与入驻、登录、审核状态、分类与菜品管理、订单处理、营业统计、店铺信息）、骑手端（登录、待接单列表、接单、送达确认、任务查询）、平台运营端（商户审核、全局查询、骑手账号维护、平台统计、操作日志）；同步定义非功能需求（安全、可靠性、易用性、可维护性）与关键业务规则（数据作用域、状态机、AI 安全规则、审计要求）。

（3）**业务口径收敛。** 按最小可行原则明确本期范围与"本期不包含"清单（退款、菜品规格与 SKU、真实支付、推送、复杂配送调度等），保证需求范围可控、口径唯一（如配送费为平台固定值、订单状态以整数枚举为唯一真值）。

### 2. 系统总体设计

（1）**架构设计。** 采用前后端分离架构：后端基于 Django 提供 JSON 接口（统一响应格式 `{code, info, data}`）；前端采用 Vue 3 + Vite + TypeScript 构建顾客端、商户端、骑手端三个独立单页应用（npm workspaces 单仓库多应用，共享请求封装与状态口径）；平台运营端由 Django Admin 承载；前端构建产物由 Django 同源托管，实现单端口部署演示。

（2）**技术选型论证。** 后端选择 Django 的四点理由（Admin 开箱即用、ORM 与迁移一体化、认证体系可复用、教学规模下性能非瓶颈）；数据库默认 SQLite（零配置）、可通过环境变量切换 MySQL 8；AI 能力采用 OpenAI 兼容的函数调用接口，未配置模型凭据时自动降级为内置规则化实现（保证演示可靠性与可复现性）。

（3）**数据库设计。** 基于业务主线设计二十余张数据表，划分用户域、商户域、商品域、订单域、支付域、配送域、评价域、运营审计域与 AI 服务域；金额字段使用 Decimal；订单明细对菜品名称与单价做快照；关键字段建立索引与唯一约束；给出 E-R 关系与表结构说明。

（4）**关键机制设计。** 订单状态机（状态取值 10–60，合法迁移表与统一变更入口，非法迁移拒绝并记录日志）；四类角色独立盐值的令牌认证；服务端作用域过滤（商户/顾客/骑手按作用域隔离数据）；操作审计（含 AI 工具调用）。

### 3. 关键技术实现

（1）**受控 AI 下单机制（核心创新点）。** 设计并实现七个 AI 工具接口（商户搜索、菜品搜索、草稿校验、草稿生成、订单状态查询、催单、评价），以 OpenAI 兼容 JSON Schema 声明供模型调用；实现多轮工具调用循环（对话代理）与系统提示词约束；实现"后端重校验"（价格、库存、商户归属以数据库为准）与"草稿单"机制（AI 只生成待确认草稿，正式订单由顾客确认后服务端创建）；实现工具调用全程审计（记录操作者标识、动作、参数与结果）。

（2）**安全与隔离实现。** 实现四类角色独立盐值令牌的签发与校验；实现统一权限装饰器体系（登录校验、商户审核门槛等）；实现数据作用域过滤（查询与写操作强制携带作用域条件）；实现下单地址校验、订单归属过滤等业务安全校验，并以测试用例验证跨商户、跨顾客、跨骑手越权请求均被正确拦截。

（3）**功能实现与测试。** 完成后端各业务模块、前端三端界面与 AI 助手的编码实现；编写自动化测试覆盖作用域越权、状态迁移合法性、业务口径（配送费、展示字段）与入驻链路等场景；完成全链路端到端验证（下单→支付→接单→配送→评价→AI 对话下单）。

（4）**AI 功能评估。** 构造对话测试用例集，统计三个量化指标：槽位字段准确率（商户/菜品/数量/地址四类字段与期望值的一致比例）、下单耗时（AI 辅助下单与人工逐项下单的耗时对比）、非法状态与越权测试通过率（构造非法请求的被拦截比例）。

### 4. 论文撰写与答辩准备

整理需求分析、系统设计、测试与评估数据，按学校规范撰写毕业论文；准备系统演示环境与答辩材料，完成毕业答辩。

## 三、课题研究的条件（材料、主要实验仪器设备等）

**硬件：**

- 操作系统：Windows 11 专业版
- CPU：四核 2.0GHz 以上
- 内存：8GB 以上
- 磁盘：20GB 以上可用空间

- 开发语言与框架：Python 3.12、Django 6.1；Vue 3 + Vite + TypeScript（Node.js 22）

- 接口测试工具：Postman / curl / Django Test
- 模型服务：大语言模型对话接口（OpenAI 兼容 API，按量调用；未配置时使用内置规则化实现）
