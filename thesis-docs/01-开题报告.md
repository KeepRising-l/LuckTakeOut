## 一、选题背景与意义

### 1.1 选题背景

随着移动互联网与即时配送行业的快速发展，网络订餐外卖已成为餐饮消费的重要形态。以美团、饿了么为代表的大型外卖平台，本质上都是**多商户（多租户）**平台：平台作为运营方，接入并审核大量入驻商家（商户），商户各自维护自己的菜品、库存与订单，消费者在平台内跨商户浏览、下单，平台负责交易监管与订单流转。这种"一个平台、多方参与"的业务形态，对系统的**数据隔离、权限控制、交易一致性**提出了较高要求。

对高校教学与中小型场景而言，直接照搬大型平台的分布式架构既不必要也不现实。因此，如何用**单一、可控的技术栈**实现一个具备多商户核心业务闭环（商户入驻与审核、菜品管理、购物车、下单、支付、订单流转）的外卖平台，是一个兼具工程性与教学价值的问题。Python 语言生态成熟、开发效率高，Django 框架自带 ORM、权限系统与管理后台，适合作为此类平台的后端实现；前端采用 Vue 3 单页应用，与后端通过 JSON 接口通信，便于三个不同终端（顾客、商户、骑手）各自组织界面。

与此同时，大语言模型（Large Language Model, LLM）与**函数调用（Function Calling）**技术的成熟，使得"用自然语言对话完成业务操作"成为可能。面对"对话式下单"这一典型场景，如何让模型在**不完全可信**的前提下安全地参与业务流程（而不是直接修改数据库或发起扣款），是一个值得研究的问题。

### 1.2 选题意义

**理论意义：** 本课题探索大语言模型在受控业务系统中的落地范式——模型只承担"意图理解与槽位抽取、生成待确认草稿"的职责，真实的数据写入与资金操作始终由后端按业务规则重新校验后执行。该范式对"如何在业务系统中安全地引入 AI 能力"具有参考价值。

**实践意义：** 本课题将完成一套基于 Python 的多商户外卖平台，覆盖商户入驻与审核、菜品管理、购物车、下单、支付（模拟）与订单状态流转等核心业务，并在此基础上实现一个顾客端内置的"AI 点餐助手"。成果可直接用于教学演示，也可为中小型多商户平台的快速搭建提供参考。

## 二、国内外研究现状

### 2.1 外卖平台与多商户系统的研究与应用现状

国外方面，Deliveroo、Uber Eats、DoorDash 等平台较早形成了多商户聚合外卖的商业模式，其系统普遍按照商户、订单、配送、支付等业务领域进行模块划分。国内方面，美团、饿了么在订单调度、峰值削峰、多商户结算等方面积累了大量工程实践；开源社区中亦存在大量"外卖/点餐系统"教学项目，但多数为**单商户**（即单个餐饮企业自营点餐），对多商户的审核、隔离与平台运营支持不足。

### 2.2 对话式交互与智能点餐的研究现状

近年来，基于 LLM 的智能体（Agent）成为研究热点。ReAct 提出将"推理"与"行动（工具调用）"结合，使模型能够在推理过程中调用外部工具；Toolformer 进一步证明模型可以自主学习何时调用工具。工业界随即将**函数调用（Function Calling）**标准化，使模型能以结构化参数调用后端接口。

在点餐场景，已有研究尝试用对话机器人完成菜品推荐与下单，但普遍存在两个问题：一是模型输出不可控，可能在价格与库存上产生"幻觉"；二是缺少对模型操作的审计与越权防范。**如何把对话式下单与严格的后端校验、权限隔离、操作审计结合起来**，是本课题关注的重点。

### 2.3 现状小结

综上，多商户外卖平台在工程上已有成熟经验，但开源实现多偏向单商户或过度复杂的分布式架构；对话式下单在技术上可行，但安全性与可控性仍缺乏系统化的处理方案。本课题拟结合二者，用 Python 技术栈实现多商户外卖平台，并引入"AI 生成订单草稿 + 后端重校验 + 顾客确认"的可控 AI 下单流程。

## 三、研究内容与目标

### 3.1 主要研究内容

1. **多商户外卖平台的设计与实现**：商户注册与入驻审核、商户信息与菜品（含分类）管理、消费者浏览与购物车、下单与模拟支付、订单状态流转、平台运营管理。
2. **多商户数据隔离与权限控制**：保证商户只能管理自己的菜品与订单，消费者只能访问自己的订单，防止跨商户越权操作。
3. **订单状态机设计**：定义订单从"待支付 → 已支付 → 待接单 → 配送中 → 已完成"以及"可取消状态 → 已取消"的合法迁移与非法迁移拦截。
4. **顾客端 AI 点餐助手**：顾客在顾客端内通过自然语言对话收集"商户、菜品、数量、地址"等信息，由模型调用后端工具生成**待确认订单草稿**；价格、库存、商户归属由后端重新校验，顾客确认后才生成正式订单。
5. **操作审计**：记录 AI 与人工的关键操作（操作者、动作、前后状态），支持追溯。

### 3.2 拟解决的关键问题

1. **模型输出不可信问题**：通过"草稿单 + 后端重校验 + 顾客确认"机制，使模型无法直接影响真实数据与资金。
2. **对话槽位到结构化订单的映射问题**：设计对话状态与槽位（slot）填写逻辑，处理缺槽、歧义与用户改口。
3. **多商户越权与非法状态问题**：通过服务端作用域校验（merchant_id）与状态机校验，保证数据隔离与流程合法。

### 3.3 研究目标

完成一套可运行的多商户外卖平台，并实现可控的 AI 对话式辅助下单功能；通过实验验证其在**槽位字段准确率、下单耗时、非法状态与越权测试通过率**等方面的表现。

## 四、研究方法与技术路线

### 4.1 技术选型

| 层次 | 选型 | 说明 |
| --- | --- | --- |
| 开发语言 | Python 3.x | 与课题"基于 Python"一致 |
| Web 框架 | Django | 自带 ORM、数据库迁移、认证与权限、管理后台，适合多商户建模 |
| 数据库 | SQLite（默认）/ MySQL 8（可切换） | 开发与演示用 SQLite 零配置；通过环境变量可切换至 MySQL 8，事务保证订单一致性 |
| 前端 | Vue 3 + Vite + TypeScript（三端单页应用） | 顾客端、商户端、骑手端各自独立构建，通过 JSON 接口与后端通信；npm workspaces 组织为单仓库多应用 |
| 前后端通信 | REST 风格 JSON 接口 | 统一响应格式 `{code, info, data}` |
| 管理后台 | Django Admin | 平台运营端（商户审核、查询、统计、操作日志）直接由管理后台承载 |
| AI 能力 | 大语言模型 Function Calling | 由模型调用后端工具，不直接访问数据库 |
| 开发方法 | 迭代式开发 | 先主线、后扩展 |

**关于 Web 框架的选择（Django 而非 FastAPI）：**

1. **管理后台开箱即用**：本课题的平台运营端（商户审核、商户/用户/订单查询、操作日志、骑手账号维护）直接由 Django Admin 承载，无需另写前端与后台接口。FastAPI 本身不提供管理后台，需自行开发或引入第三方组件，而运营端恰是多商户平台不可缺少的一环。
2. **ORM 与数据库迁移一体化**：平台涉及十余个业务模块与二十余张表，Django 的模型定义与迁移机制由同一套体系管理；FastAPI 需要另行组合 ORM 与迁移工具，配置与概念层数更多。
3. **认证与角色体系可直接复用**：`django.contrib.auth` 提供用户、密码存储、会话与 `is_staff` 等基础能力。本系统四类角色均建立在其之上（顾客、商户、骑手各自关联一个账号，运营身份用 `is_staff` 表达）。
4. **FastAPI 的优势与本课题的痛点不重合**：FastAPI 的长处在于异步高并发、类型驱动的请求校验与自动生成的接口文档；本课题定位为教学演示规模（单机、SQLite、数十个接口），吞吐量并非瓶颈，而接口契约由需求与规格文档统一约定（见 4.2 第 1 步），因此自动文档带来的收益有限。

### 4.2 技术路线

1. 需求分析与建模：确定用例、领域实体与关系，并将需求固化为可验证的规格（每条需求对应可观察的验收场景），作为后续设计与测试的依据。
2. 数据库设计：完成 E-R 图与表结构设计。
3. 后端开发：按模块实现顾客、商户、菜品、订单、支付、配送、审核与审计。
4. AI 模块开发：设计工具接口（搜索商户、搜索菜品、校验草稿、创建草稿、查询订单状态、催单、提交评价），实现对话与槽位管理。
5. 前后端联调与测试：功能测试、越权与非法状态测试、AI 效果评估。
6. 论文撰写与修改。

### 4.3 AI 下单流程（核心流程）

```
顾客在顾客端打开 AI 点餐助手 → 对话收集槽位(商户/菜品/数量/地址)
            → AI 调用工具获得候选并组合
            → 后端重校验(价格/库存/商户归属/地址合法性)
            → 生成待确认订单草稿(OrderDraft)
            → 顾客确认
            → 草稿转为正式订单 → 模拟支付
            → 记录操作审计
```

### 4.4 评估方法

- **槽位字段准确率**：对测试用例集统计 AI 抽取的字段（商户/菜品/数量/地址）与期望值的准确率。
- **下单耗时**：对比"AI 辅助下单"与"人工逐项下单"的平均耗时。
- **非法状态与越权测试通过率**：构造跨商户访问、跨顾客访问、非法状态迁移等用例，统计系统的拦截成功率。

## 五、预期成果与创新点

### 5.1 预期成果

1. 一套可运行的多商户外卖平台系统（含源码与部署说明）。
2. 毕业论文一篇。
3. 需求分析、系统设计、数据库设计、测试等文档。
4. AI 辅助下单的实验数据与分析。

### 5.2 创新点

1. **可控的对话式辅助下单**：AI 只生成"待确认订单草稿"，不直接写库、不直接扣款，真实下单必须经后端重校验与顾客确认。
2. **AI 操作的可审计性**：将 AI 的关键动作纳入操作日志，支持追溯。
3. **AI 与业务共用同一套安全边界**：AI 调用的工具接口与人工请求走同一套认证、作用域校验与业务规则，AI 不享有任何特权通道。
4. **可量化的评估**：以字段准确率、下单耗时、越权/非法状态测试衡量 AI 功能的实用性与安全性。
